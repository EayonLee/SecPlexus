# 01 · 业务架构

> 用大白话说：SecPlexus 收各家的告警，把它们按攻击事件归好组，AI 分析师逐组调查给出结论，人只需要在三队列工作台里做判断和授权，处置动作由 SOAR 执行并回写回用户的原系统。整个过程越用越准——因为每次人工纠正都沉淀成了机构记忆。

## 1. 产品定位：四根支柱，一个底座

### 1.1 姿态：替换大脑，不与厂商竞争

这个定位回答的是商业问题，先于技术问题。多数企业已经采购了各家安全厂商的 SOC/EDR/WAF——再造一个重 SOC 是跟整个安全行业竞争，而做"替换他们的大脑"是站在所有厂商之上：

```
   用户已采购的厂商栈（躯干，继续用，不换）
   ┌────────────────────────────────────────────┐
   │  SIEM( Splunk/NGSOC )   EDR   WAF   云安全   │
   │        ▲                                   │
   │        │  告警上行 / 处置回写（原生 ID）        │
   └────────┼───────────────────────────────────┘
            │
   ┌────────┴───────────────┐
   │   SecPlexus（大脑）      │  跨厂商关联 · AI 研判 · 处置编排
   │   "指挥手脚干活"          │  处置动作由厂商设备执行并回写
   └────────────────────────┘
```

**第一价值主张是提效减负**。行业研究【Vectra AI 2023–2026】给了这组数字：SOC 平均每天收到 4,484（2023）→ 3,832（2025）→ 2,992（2026）条告警，**被忽略的比例始终在 63–67%**——告警量在降，处理能力没有跟上；单条告警人工调查平均约 70 分钟（D3），一个四人 SOC 每周只能深查 300–400 条高保真告警、其中 90% 是良性（Prophet）。这就是用户说"上了 SOC 事情反而变多了"的定量版本：**传统 SOC 给了检测能力，没给处理能力**。我们的验收指标因此定为"分析师每天要看的告警数和工时"（对齐 Radiant 的表达：每分析师每天只升 1–3 条），不是功能清单。

### 1.2 为什么用户需要第三方大脑

厂商自己都在做 AI（Sentinel Copilot、CrowdStrike Charlotte、阿里安全运营 Agent），第三方大脑的存在理由是结构性的：

| 厂商 AI 的边界 | 第三方中立层的对位价值 |
|---|---|
| 只在自家遥测内推理——异构栈（Splunk + 深信服 + 齐安信 + 云）里全是盲区 | 坐在**任何检测层之上**，跨厂商关联还原同一次攻击（"XDR 天花板"命题的解法，D3 Security 论证） |
| 绑定自家生态，AI 成为进一步锁定的杠杆 | 中立层天然多厂商，处置回写用每家的原生 ID |
| 厂商没有动力告诉你"别家看得更清楚" | 跨源研判的中立结论 |

一个警示同样来自市场：KuppingerCole 统计已有 **123 家 AI SOC 厂商**，其中大量只是往现有工具上糊一个 copilot 聊天框。我们的差异不在"有 AI"，而在**数据面质量（归一化/实体/资产）+ 研判闭环（记忆/规则建议/影子模式）+ 处置回写**——这三个都是工程，不是 prompt。

### 1.3 AI 助手 vs AI-native：为什么厂商做不好

厂商自有 AI 普遍是"助手"而非"原生"，这不是能力问题，是被自己的存量架构锁死的：平台是资产也是枷锁，在已有 SOC 平台上加 AI 的最小改造路径就是"通用 agent 框架 + 平台 CLI 外挂 + 方法论 prompt"——但这条路的天花板就是助手。

从国内厂商已发布产品的公开演示与文档看，AI 助手形态收敛为同一个结构：**通用 agent 内核（模型-工具循环）+ 平台数据 CLI + 研判方法论 prompt 技能包**。即便工程细节做得认真（工具返回区分"无数据"与"失败"、并行调用、边查边报、权限边界），结构上的限制是一致的：

- **触发条件都是"用户要……"**——人发起、AI 响应，运营的主体还是人；
- **研判流程活在 prompt 方法论里**（技能文件靠人工维护版本）——无法进 CI、无法做确定性门禁、无法回归测试；
- **输入单元是单条告警**——没有跨源事件归并，"同一实体 3 分钟前的相关告警"要靠模型自己在会话里查；
- **没有闭环**——会话结束知识就散了，没有结论沉淀、没有纠正回流、没有规则建议。

公开数据同样支撑"助手解决不了效率问题"：Microsoft 的自主 agent 被一线用户评"mid"、低慢攻击是盲区【实测·Reddit】；腾讯公开承认单 agent 成功率 75%【官方文档】。**业界 2026 年的共识表述**：AI-native 是"AI 设计进架构、数据流、决策与治理的地面起方案"，而在遗留平台上外挂 copilot 无法修复检测与处理的根本缺口【行业研究·[HivePro](https://www.hivepro.com/blog/ai-native-soc-architecture-workflows-governance) / [databahn](https://www.databahn.ai/blog/what-an-ai-native-soc-actually-looks-like) / [Exabeam](https://www.exabeam.com/explainers/ai-cyber-security/ai-native-vs-ai-enabled-5-differences-and-security-considerations)，详见 04 §5.3】。

两种模式的分野，逐维度对照：

| 维度 | AI 助手（copilot 外挂） | AI-native（SecPlexus） |
|---|---|---|
| 触发 | 人发起会话 | 数据驱动：告警/事件组自动触发，人只处理队列 |
| 研判输入单元 | 单条告警/单会话 | **事件组**（跨源聚合 + 攻击链） |
| 研判流程 | 活在 prompt 方法论里，人工维护版本 | **图编排骨架**（代码、可测试、可门禁、可进 CI） |
| 治理 | prompt 措辞约束（"没有证据不要改状态"） | 系统约束（groundedness 门禁、影子模式、earned grant） |
| 记忆 | 会话内上下文 | **机构记忆飞轮**（结论沉淀 + 纠正强制填因 + 规则建议） |
| 验收 | 演示效果 | 影子数据、检出率、每分析师每天条数 |
| 上下文管理 | 手工预算标注 | 实体档案 + 知识前置过滤的结构化供给 |
| 为什么做不成 AI-native | 存量平台锁死：通用 agent + CLI 外挂是不动架构的唯一路径 | 我们没有存量包袱，数据面为 AI 而建 |

"AI-native"在这套文档里不是口号，是上面这张表——每一行都对应 02 里的一个具体设计。

SecPlexus 覆盖四条能力支柱，用威胁情报做横向底座。它与传统 SOC 的区别不是功能多少，而是运营方式：传统 SOC 呈现告警，SecPlexus 用 AI 分析师运营告警。

```
                ┌──────────────────────────────────────┐
                │        威胁情报底座（横向支撑）          │
                │     IOC / ATT&CK 映射 / 实体画像       │
                └──────────────┬───────────────────────┘
      ┌────────────┬───────────┼──────────────┬─────────────┐
      ▼            ▼           ▼              ▼             ▼
┌───────────┐┌───────────┐┌───────────┐┌────────────┐┌────────────┐
│ AI 告警运营 ││ 漏洞运营   ││ 大模型护栏  ││ 智能体安全  ││  资产基座    │
│ 降噪·归并   ││ 资产上下文  ││ Prompt注入 ││ MCP治理    ││ 主机/容器/云 │
│ 研判·处置   ││ 优先级·验证 ││ 输出DLP    ││ 供应链准入  ││ + AI资产    │
│ 闭环       ││ 闭环       ││ 越权拦截    ││ 行为审计    ││ + 指纹      │
└───────────┘└───────────┘└───────────┘└────────────┘└────────────┘
```

**结构性优势**：防护对象和运营对象是同一批资产（AI 应用、Agent、MCP server、模型 Key）。护栏拦下的一次 Prompt 注入，就是一个案件的开端——不需要为 AI 安全单独建一套运营体系。这在产品主张和架构上是一体的（见 02 的数据流图）。

护栏支柱同样遵循“替换大脑”的定位：**检测决策在 `ai-policy`（大脑），转发执行在开源网关 agentgateway（工具）**——我们不做流量转发的基础设施，只做策略与判定；这与告警支柱“研判在 agent-runtime、执行在用户设备”是同一个分工哲学。

与传统方案的边界也由此确定：**只接告警，不接原始日志**。量级差两个数量级（告警 10 万条/天 ≈ 300MB，原始日志 1 亿条/天 ≈ 100GB），用户的 SIEM 继续做日志，SecPlexus 做它做不了的那层——把多家的结论串成一个故事。

## 2. 运营对象模型：告警、事件视图、案件三层

这是整个业务架构最核心的一个决策，先给结论再给证据。

### 2.1 为什么要分三层

一条 EDR 说"编码 PowerShell 执行"，防火墙说"外连可疑 IP"，身份系统说"异常登录"——在厂商层面这三条永远不会合并（三个不同产品），但这是同一次攻击的三个阶段。运营的对象应该是"这件事"，不是三条孤立告警。

但直接照搬"安全事件运营"又会和用户的告警运营习惯冲突。解法是三层分离：

```
┌────────────────────────────────────────────────────────────────┐
│  告警（Alert）—— 持久的事实层                                     │
│  归一化后的每条告警，挂资产、挂实体、带 ATT&CK 标签                  │
│  用户的告警运营习惯 100% 兼容：永远查得到、处置得了                    │
└──────────────────────────┬─────────────────────────────────────┘
                           │ 按实体滚动聚合（TTL，可过期重建）
┌──────────────────────────▼─────────────────────────────────────┐
│  事件视图（Incident View）—— AI 的研判输入单元                       │
│  攻击链排序（"这是主机 X 上一起入侵的第 3 步"）、时间线、受影响资产      │
│  对外是告警的可选分组视图，不是另一种要运营的东西                      │
└──────────────────────────┬─────────────────────────────────────┘
                           │ 需要深挖/处置时一键立案（promote）
┌──────────────────────────▼─────────────────────────────────────┐
│  案件（Case）—— 唯一的持久运营对象                                  │
│  调查过程、研判结论、审批、处置、闭环、工单、SLA                       │
└────────────────────────────────────────────────────────────────┘
```

### 2.2 各家的做法与我们的取舍

| 参照 | 做法 | 我们的取舍 |
|---|---|---|
| 腾讯云 SOC 调查中心【官方文档】 | "自动将威胁告警基于影响资产、时间线、ATT&CK 战技术进行关联，自动还原攻击过程" | 采纳：事件视图要还原攻击链 |
| 阿里云【官方文档】 | "图计算技术将关联告警聚合生成事件，还原攻击链并提取恶意实体" | 采纳：实体提取 |
| 火山引擎安全运营智能体【官方文档】 | "将分散的原始告警收敛为实体事件……AI 以组为单位研判" | 采纳：**AI 以事件组为研判单元**（省 token + 上下文完整） |
| Microsoft Defender XDR | 最多 150 条告警合成 1 个 incident，分析师待办就是 incident 列表 | 印证：平台型都做聚合 |
| AiSOC【代码】 | `IncidentSummary` **存在 Redis 里带 TTL，不落 PG**；攻击链同样 fuse 时滚动 | 采纳：事件视图做成轻量聚合，不建重实体 |
| TheHive | alert → promote → case 的转案模型 | 采纳：立案是核心动作 |
| flocks【代码】 | 只有 `alert_records`，告警直达研判 | 不采纳：它是工具形态，我们是平台形态 |
| OCSF【官方文档】 | `detection_finding`(2004) 是告警，`incident_finding`(2005) 是案件 | 采纳：案件直接映射 2005 的状态机/置信度/工单字段 |

一句话：**告警是事实、事件是视图、案件是对象**。AI 的结论落回每条告警；习惯告警运营的用户用告警列表，习惯事件运营的用户切事件视图，默认视角按租户配置——零冲突。

## 3. 资产基座：封禁之前先知道封的是什么

资产不是配置页里的清单，是运营的地基。第一用途就是**处置的爆炸半径门控**：错误的封禁比攻击本身更贵（2024 年 CrowdStrike 一次错误更新造成全球宕机的教训），所以 SOAR 执行任何封禁/隔离前必须查资产——这是生产数据库还是测试机？高危资产强制升级审批，AI 提议不允许直接执行。

```
资产用途优先级：

① 处置爆炸半径门控（封禁前查关键性，高危资产强制人审）    ← v1
② 研判上下文（同一条告警在测试机和生产核心库上优先级不同）  ← v1
③ AI 资产清单（应用/模型/Agent/MCP/Key）= 产品差异化落点    ← v1
④ 攻击路径分析（漏洞+暴露+配置 → 路径）                    ← v2
⑤ 漏洞运营的前提（漏洞挂资产才有优先级）                    ← v2
⑥ 影响面评估（事件涉及哪些业务）                            ← v2
```

【官方文档】阿里云资产指纹采集到账号/端口/进程/中间件/数据库/Web 服务/软件/计划任务/启动项/内核模块/Web 站点共 11 类；腾讯云把"统一资产基座（主机、容器、**AI 资产**、云产品）"列为核心理念第一条。v1 我们只做最小集：**清单 + 关键性等级 + 手工导入/云同步**，够门控和研判用。

**环境相关性判断**是资产的隐藏用途【实测·Dropzone/SANS 评审】："如果环境里根本没用 log4j，log4j 告警就不该占用分析师时间"——资产参与检测相关性，是降噪的另一个维度。

## 4. 三队列工作台：把不确定性做成一等公民

工作台（不是查询页）是运营的主界面。形态来自火山引擎【官方文档】，这是目前看到的最诚实的人机分工设计：

```
┌───────────────────────────────────────────────────────────────┐
│                      三队列工作台                                │
├───────────────────┬───────────────────┬───────────────────────┤
│  ① AI 已研判       │  ② AI 不确定       │  ③ 已闭环              │
│     等你授权        │     需要你的认知    │     不打扰你            │
│                   │                   │                       │
│  核对处置对象/证据/  │  缺资产用途/账号归  │  定期抽查 +             │
│  影响范围后授权，或  │  属/变更背景——补信 │  「我要纠错」入口        │
│  直接纠正 AI 的方案  │  息后重新研判       │                       │
└───────────────────┴───────────────────┴───────────────────────┘
        分流依据：AI 是否能够判断 × 是否具备可执行的处置能力
```

配套的产品指标表达学 Radiant【实测】：不说"降噪 97%"，说"**每分析师每天只升 1–3 条高保真告警**"——把降噪翻译成人的工作量。

## 5. AI 研判闭环：四个飞轮

单次研判只是流水线，闭环才是 AI SOC 与传统自动化的区别。四个机制让系统越用越准：

```
                    ┌─────────────────────────────┐
                    │        AI 研判（假设驱动）      │
                    └───┬─────────────────┬───────┘
          ①机构记忆      │                 │ ②知识前置过滤
     研判结论沉淀 ◀──────┘                 └──────▶ 规则/知识库先过滤，
     分析师纠正（强制填原因）写回                     只把剩下的给 LLM
            ▲                                     （token 第一道闸）
            │ ③规则建议闭环
            │    AI 从误报反哺归并/检测规则
            │    propose → 人审 → eval 门控 → 上线
            │                                     ▲
            └── ④攻击链滚动聚合 ───────────────────┘
                 correlator 归并时按实体+kill-chain 阶段滚动（TTL），
                 UI 显示"这是入侵的第 K 步"
```

### 5.1 机构记忆（Context Memory）

【实测·Dropzone】记忆有三个来源，缺一个都不完整：

1. **过往调查**——历史研判中发现的用户-账号-设备-IP 关系
2. **分析师纠正**——人工改结论时**强制填写原因**，原因入库（没有原因的纠正只是标签，有原因的纠正才是可复用的知识）
3. **用户直录**——"这个 IP 段是测试环境""这个团队做安全测试"

存储用向量库组织，调查时自动应用。**按组织（org）隔离**：每个部门的记忆是自己的经验，互不可见（全局威胁情报除外）。定位是"完美回忆"：人类分析师会忘记或不对齐地应用环境知识，AI 每次调查都带全量上下文。【代码·AiSOC】`institutional_memory` 表已验证此模式，分析师覆盖以 `analyst_override=True` 与 agent 结论同库检索。

### 5.2 知识前置过滤

【官方文档·火山引擎】告警在进 LLM 之前先用知识库过滤。这是成本控制的第一道闸，和确定性归并降噪（见 02）配合：**能用规则挡掉的绝不花钱问模型**。

### 5.3 规则建议闭环

【代码·AiSOC】`detection_proposal` 实现了 propose → review → eval-gated → promote 的工作流。误报不是白来的——每次误报都是一条可学习的样本，反哺成两类建议：**我们自己归并策略的修改**（直接生效路径），以及**用户上游 SIEM 检测规则的调优建议**（经人工评审后由用户在他们的系统里改——大脑指挥手脚的又一处体现：我们不做检测引擎，但让厂商的规则越用越准）。

### 5.4 攻击链滚动聚合

【代码·AiSOC `attack_chain_grouper`】AiSOC 在 fuse（归并）时按实体查/建 `chain_id`（Redis 滚动 TTL），把后续同实体告警按 MITRE kill-chain 阶段排序挂进链，fail-soft（Redis 故障降级为无链，不报错）。我们对应为 correlator 归并时执行同款机制。分析师看到的第一眼就是"这是一起 20 分钟前从初始访问开始的入侵的第 3 步"。

姊妹机制：**组织可信制品库**【实测·Intezer】——环境内已知合法的 hash/制品参与判定（"这个 hash 在你们环境是常见合法软件"）。机构记忆记"结论"，可信库记"什么在此环境是正常的"。v1.5。

## 6. 影子模式与挣得的授权（Shadow Mode & Earned Grant）

自动化放权的方式不是配一个置信度阈值，而是**按告警类别逐类挣得**：

```
第 1 周～N 周（影子模式）                    之后（授权评审）
┌────────────────────────────┐            ┌─────────────────────────────┐
│ AI 说"这类我可以自动关"       │            │ 统计每类告警的影子正确率：       │
│ → 只记录，不执行             │ ─────────▶ │ "扫描器探测"类连续 30 天零错判   │
│ 数据从第一天开始攒            │            │  → 挣得 auto_close 授权       │
└────────────────────────────┘            │ "特权账号异常登录"类未挣得       │
                                          │  → 永远人审                   │
                                          └─────────────────────────────┘
```

类比：新员工试用期。不能因为整体准确率 85% 就给关单权——按工种考核，考核通过的工种才放权。

这不是我们的发明，是从一次真实事故里学来的【代码·AiSOC ADR-0009】：置信度 > 0.85 就自动关单导致自信的误报被静默关闭；更糟的是配置了策略的租户反而被锁死（查询写错了表），"谨慎的配置比不配置更危险"，两个方向都错过。正确形态：授权按类别发、可撤销、审计留痕，**全局阈值一刀切被禁止**。

v1 就要有影子模式的框架——哪怕零授权，因为数据必须从第一天开始攒，否则永远没有"挣得"的依据。

## 7. 深度调查：告警威胁溯源

三队列里"需要深挖"的案件进入深度调查：从研判结果一键带入上下文，多轮对话还原攻击全貌，产出结构化调查报告【官方文档·火山引擎"深度调查"同款】。区别于自动研判的批处理模式，这是交互式的，但全程 Ledger 留痕。

能力边界要诚实（见 02 §6）：TP/FP 判定前沿模型能到 96–98%，**深度调查只有 40–60%**——所以深度调查是"人主导、AI 加速"，不是"AI 主导、人监督"。

调查产物 v1 做成结构化报告；**Notebook 化（调查 = 可执行、可重放的制品）**是 v2 后置项——Rally / Azure Sentinel 的 "Software Defined Monitoring" 验证过该形态（模板化调查保证一致性、产物挂回案件），但对 v1 太重。

## 8. 处置与回写

处置执行三个铁律（证据见 02 §5 的数据模型）：

1. **Agent 提议，SOAR 执行**——AI 不隔离主机、不禁用账号、不封域名【实测·Dropzone 把这条做成了卖点："这正是两种技术互相配合而不是抢同一份工作的原因"】
2. **按上游原生 ID 回写**——我们合并出的平台 ID 只做内部审计；回写用户的 SIEM/工单必须用他们的原生 ID（NGSOC 的 `alarmIds`、Splunk 的 notable id）
3. **良性关闭必须是"有文档的结论"**，不是"无解释的关闭"——分析师可以抽查每一次自动决策【实测·Dropzone 原话】
