> 用大白话说：9 个自研服务 + 4 个开源组件跑在 PostgreSQL 和 Redis 上。数据从左边流进来（告警 + AI 流量两条入口），经过归并降噪变成告警和事件视图，AI 在图编排的骨架里研判，人批了以后 SOAR 执行处置回写回原系统。存储只上一个 PG（量级算过账），检索不自研发语言。

## 1. 服务清单与拆分理由

服务拆分的判据不是"功能不同"，而是以下五条之一：**独立扩容**（瓶颈维度不同）、**故障隔离**（会卡住会崩溃）、**独立变更**（改动频率不同）、**技术栈强制**、**安全边界**（高危能力单独管控）。

### 1.1 v1 全景（自研 8 组件（Python×7 + web 前端），2 镜像；开源 4 组件）

| # | 服务 | 类型 | 语言 | 职责 | 为什么拆 |
|---|---|---|---|---|---|
| 1 | `collector` | 自研 | Python | 一切外部数据的唯一入口：告警接入、形状判别、OCSF 归一化、L0/L1 校验 | 改动最频繁（每接一家厂商就改），独立发版；突发流量独立扛 |
| 2 | `correlator` | 自研 | Python | D1 去重 → D2 窗口折叠 → D3 跨源关联 → 告警 + 事件视图（攻击链） | 吞吐瓶颈，纯 CPU，按 `org:entity` 分区保序扩容 |
| 3 | `agent-runtime` | 自研 | Python（内嵌 LiteLLM SDK + NeMo Guardrails 库） | 全部 AI 推理：研判 Agent（图编排骨架）、NL→查询、**guardrail 检测 API**（ai-policy 的模型类检测调这里） | **LLM 有 1/4 概率超时/无结果**【官方文档·腾讯实测】，必须和管线故障隔离——部署时独立容器（同镜像 SPX_ROLES=agent） |
| 4 | `soar` | 自研 | Python | **通用 workflow/playbook 引擎宿主**（orchestrator 库）、预案库、审批状态机（持久化暂停）、高危动作执行、按上游原生 ID 回写；通知（邮件/IM/工单）是 governed action | 安全边界：Agent 提议 / SOAR 执行的权限分界 |
| 5 | `ai-policy` | 自研 | Python | AI 安全策略大脑（独立 PDP，SpiceDB/Cerbos 同款形态）：规则、ext_authz 决策、事件回流、管理 API。**检测分两层**：规则类（正则/关键词/schema）内存匹配走同步路径（亚毫秒）；模型类（语义级注入/越权）异步调 agent-runtime 的 guardrail API（NeMo 库内嵌于彼） | 独立 PDP 是行业标准形态；同步路径只有规则不阻塞客户流量 |
| 6 | `iam` | 自研 | Python | 登录、SSO（OIDC/SAML）、RBAC/ABAC、多租户、API Token、SCIM | 身份是核心攻击面，被所有服务验签 |
| 7 | `console` | 自研 | Python / FastAPI | 查询（热层同步/狩猎异步）、Case、三队列工作台、SSE、资产与连接器配置 | 长尾查询 + 高危操作边界 |
| 8 | `web` | 自研 | TypeScript / Next.js | 前端 | 技术栈强制 |
| 9 | `scheduler` | 自研 | Python | 全部**平台级**定时任务的唯一入口：情报拉取、报表、蜜标巡检、供应链扫描 | **基础设施组件（cron 哲学：简单、稳定、永不失败）**：任务代码内声明 + DB 持久化 + 分布式锁单实例；与 playbook 的 schedule 触发器分层——用户业务流定时归 orchestrator，平台心跳归这里，基础设施不依赖业务引擎 |
| 10 | `ai-gateway` | **开源** | agentgateway（Rust） | 哑数据面：用户 AI 流量（LLM+MCP）的 inline 治理，决策回调 #5 | 只依赖 xDS + ext_authz 两个稳定协议，升级不被绑定 |
| 11 | `postgres` | **开源** | PostgreSQL 16 | 主存储 | — |
| 12 | `redis` | **开源** | Redis 7 | 队列（Streams）、去重窗口、限流 | 去重要带 TTL 的高频读写 |
| 13 | `object-storage` | **开源** | MinIO / S3 兼容 / 本地 FS | raw payload、Parquet 归档 | raw 永不进主表 |

**两个容易混淆的区分**：`ai-gateway` 管的是**用户**的 AI 流量（防护对象），agent-runtime 内嵌的 LiteLLM SDK 管**我们自己**调模型的流量（内部出口）——方向相反不能共用；`soar` 与 `agent-runtime` 的分界是"想"和"做"——高危动作不能跑在 AI 进程里。

**语言版图**：当前 Web 使用 TypeScript/React，IAM 与 Console 使用 Go，根 Go module 统一管理服务及共享包。后续 AI 能力可按实际生态选择 Python；跨语言依赖通过公开契约隔离，不因语言选择增加不存在的服务或生成多套协议真源。workflow/playbook 等后续服务的选择由各自需求方案确认。

**组件 / 角色 / 镜像**：组件（代码域）→ 角色（部署单元，`SPX_ROLES` 决定；agent 因 LLM 故障隔离部署为独立容器，同镜像同语言）→ 镜像（交付物，**自研仅 2 个**：`secplexus` Python 全角色 / `secplexus-web`）

## 2. 数据流：以数据流入为主轴

架构图从数据流入开始，用户操作是旁挂的控制平面——数据永远不经过人。

════════════ 控制平面（页面操作，旁挂不穿流）════════════

三条设计要点：

1. **两条数据源的汇合点在 ①**——`ai-policy` 拦下的注入事件回流 `collector`，从此和 EDR 告警走完全相同的链路。"防护对象 = 运营对象"在架构上就这一条线。
2. **跨阶段连接全靠队列不靠调用**——①→② 走 Redis Stream，②→③ 走 Case 事件；任何一级慢了或挂了，上游照常摄入，恢复后接着跑。
3. **`worker` 和 `agent` 必须分进程不是洁癖**——LLM 卡住会阻塞去重；且两者扩容维度完全不同（CPU 密集 vs 网络等待密集）。

## 3. 数据模型

### 3.1 核心实体

```
assets            资产（含 AI 资产）+ 指纹；关键性等级（处置门控用）
alerts            告警：OCSF 2004 结构 + 实体抽取 + ATT&CK + chain 元数据
                  + source_refs[]（上游原生 ID 映射，一对多）
                  + aggregation_evidence（上游合并探测三档置信）
incident_views    事件视图：Redis 滚动 TTL（不建重表）+ 告警上的 chain 字段
cases             案件（OCSF 2005）：状态机 + case_tasks + case_timeline
investigations    调查 Ledger：Run / Event / Artifact（prompt、工具调用、引用全量）
institutional_memory  机构记忆：结论沉淀 + 分析师纠正（reason 必填）+ 用户直录
rule_proposals    规则建议：propose → review → eval-gated → promote
shadow_decisions  影子模式记录：从第一天攒，授权的依据
entities          实体档案（IP/账号/主机/hash）：画像、历史、关系（agent 的上下文底座）
```

**三条贯穿性设计**：

1. **`org_id` 进所有业务表的主键/唯一键**（组织概念见 §3.4）。这是"架构上支持未来多集群"的真正含义——不是现在就上多集群，而是现在不做未来拆不动的事：届时无论逻辑复制按组织拆分还是 hash 分片，都不用改表结构。
2. **保留策略 = 工作记忆模型**（详见 §6.1）：归一化告警 90 天滚动窗口（按天分区过期自动清）、raw payload 7–30 天可配、事件视图 TTL 滚动；**案件、调查 Ledger、机构记忆/影子决策永久**（大脑的产出与经验）。
3. **证据自包含原则（由 2 推出，防止 90 天清理割裂永久案件）**：案件和 Ledger 在结案时保存**证据快照**——研判依据的关键字段、source_refs、原始日志摘要冗余进 Ledger（它本来就存 prompt/工具调用/返回全文，天然自包含）。告警行过期清理**不影响**任何永久对象的完整性：案件回看证据读快照、处置回写读案件上冗余的 source_refs、影子统计读永久的 shadow_decisions 表。一句话：**告警是可再生的原料，案件和 Ledger 才是账本。**

### 3.2 归一化：OCSF 2004，不追全量映射

**【官方文档】** OCSF v1.9.0（当前稳定版）2024-11 捐给 Linux Foundation，2026-06 成为 ITU 国际标准；`security_finding`(2001) **已废弃**（since 1.1.0），新项目直接用 `detection_finding`(**2004**)。

四个必抄的机制【官方文档·OCSF 2004 定义】：

| 机制 | 作用 |
|---|---|
| `count` + `start_time`/`end_time` | 上游聚合语义的唯一标准字段——**必须读进内部模型** |
| `unmapped` | 映射不上的字段全塞这里，一条不丢——半年后排障的救命稻草 |
| `vendor_attributes` | "厂商给的值"和"我改过的值"分开存——可解释 AI 的刚需 |
| `observables[]` + `evidences[]` | 实体集中列出带路径引用，关联/富化/情报都从这里读 |

归一化分四层：**L0 最小必需集**（缺了进隔离区不进主表）→ **L1 通用实体**（actor/user/process/file/network + ATT&CK ID）→ L2 厂商专属（按需）→ L3 raw 永存。工作量比例约 7:2.5:0.5。

**六条归一化工程约束**（验证要求见 04 §4）：

1. 时间解析失败 → `null` + warning，**绝不回退 `now()`**
2. 缺失就是 `null`，不写 `"none"` 哨兵值
3. 解码顺序 UTF-8 strict → GB18030 → replace，**编码记在事件上**（国内设备大量 GBK）
4. `actor.kind` / `outcome` 判断不出就是 `unknown`，不许猜
5. 字段路径支持数组下标 + **填充率报表**（映射静默失效是常态）
6. 归一化质量门禁进 CI：填充率、warning 计数看板、schema 校验、每连接器 5–10 条回归样本

### 3.3 降噪合并：三层独立可解释

厂商合并解决"别刷屏"（单产品、单规则、同实体）；我们的合并解决"研判对象唯一"（跨产品、跨厂商、跨时间）。分层是因为混在一起就永远回答不了"这两条为什么被合并了"——用户和分析师一定会问。

| 层 | 干什么 | 键 | 输出 |
|---|---|---|---|
| D1 精确去重 | 重复投递（重放/重试/多路采集） | 同源 + external_id + 关键字段 hash | 丢弃，计数 +1 |
| D2 同源窗口抑制 | 同规则对同实体反复刷 | 同源 + rule + 主实体 + 时间窗（5–60min） | 折叠，保留 count 和时间范围 |
| D3 跨源实体关联 | 多产品告警串成一个事件 | 共享实体（IP/账号/主机/hash/域名）≥2 | 事件视图 + 关联理由（必须可解释、可一键拆开） |

**上游是否已合并判断不出来**——查遍 OCSF/ECS/ASIM/UDM/ASFF/Sentinel/QRadar 没有任何标准有 `is_aggregated` 字段【官方文档】。落地方式是接入期"合并指纹探测"报告（计数字段、ID 稳定性、时间戳对齐痕迹、上层对象 ID 七项探测），输出**三档置信度**而非布尔值：已确认聚合 / 疑似聚合 / 未观察到迹象（≠未聚合）。

**分区保序**：队列分区键必须与关联键同构，统一使用组织与实体标识组成的键，且 entity 解析顺序必须与关联键**同一份代码**——否则同一实体的告警散在不同分区被不同副本消费，序列拼错、事件一分为二，而且看起来一切正常。无实体事件回退 event_id（回退 org_id 会造成热分区）。

### 3.4 组织、权限与数据隔离（IAM 体系）

**为什么是一个 iam 而不是拆开的用户系统/权限系统/认证中心**：IAM（Identity and Access Management，身份与访问管理）是领域名称，不是微服务架构专属词——它指的就是"认证 + 用户目录 + 授权"合并的一个领域。大厂拆成独立的用户中心/权限中心是被规模（几十个系统、几万员工）逼出的**部署拆分**，不是领域本该拆分；领域上认证与授权共享同一份用户目录，小规模下拆开只有同步与一致性成本。业界常态是内置合并（Grafana/GitLab/Django/TheHive 均单体内置；Keycloak/Zitadel 本身就是合并一体的产品）。

**为什么叫"组织"不叫"租户"**：我们的隔离场景是一家公司内部的部门级数据控制，不是 SaaS 多客户——"租户"（tenant）强烈暗示后者。业界同场景的命名：TheHive 用 organisation、Grafana 用 organization、GitHub 用 organization、Zitadel 的 organization 是一等概念【官方文档】。字段统一 `org_id`。

**组织模型**：平铺 org + org 内用户组（部门内细分用组建模，不做树形嵌套——嵌套继承的可见性规则是复杂度黑洞）。一个用户可属多个 org，每个 org 一个角色。MSSP 场景天然兼容：客户公司 = org，MSSP 运营方 = 特权 org（TheHive/Zitadel 同构）。

**三层数据可见性**：

| 层 | 数据 | 可见性 |
|---|---|---|
| 全局共享 | 威胁情报 IOC、规则库、ATT&CK 映射 | 所有 org 共享（大家的情报池） |
| org 隔离 | 告警、案件、Ledger、事件视图 | 仅本 org |
| org 隔离 | **机构记忆、实体档案**（记忆隔离即此层） | 仅本 org；IOC 命中结果回流全局层 |

**告警的 org 归属在 collector 落定**：每个连接器配置属于某个 org（数据源 → org 默认），资产映射可覆盖；归属一旦落库不再变。

**iam 的职责边界（标准 PDP/PEP 分层）**——所有权限的**定义、判定、管理**收敛于 iam（策略决策点），**执行**分布在三个检查点：

```
┌────────────── iam（唯一权威源：认证 + 目录 + 授权 + 管理 + 上下文分发）──────────────┐
│ 认证：本地账号密码（Argon2id 哈希·登录锁定·会话/refresh token 轮换）· MFA(TOTP)      │
│       · OIDC/SAML 对接用户已有 IdP（飞书/钉钉/Zitadel/Keycloak 均可插拔）            │
│ 目录：组织 · 用户 · 用户组 · SCIM 同步                                               │
│ 授权：RBAC/ABAC 策略 · 全平台权限点定义（alerts:read / soar:approve / orgs:manage…）   │
│       · 菜单可见性 = 权限点的派生映射（前端登录后调 /me/permissions 按声明渲染菜单）    │
│ 管理：组织 CRUD · 用户管理 · 角色与权限分配的管理 API——Web 身份管理页面经同源入口调用它   │
│ 分发：凭据签发与会话分发（浏览器会话/服务间 JWT/API Token），全系统唯一验签点          │
└──────────────────────────┬────────────────────────────────────────────────┘
                           │ JWT / 权限点声明
        ┌──────────────────┼──────────────────┐
        ▼ 执行点①API       ▼ 执行点②数据        ▼ 执行点③前端
        每个服务的中间件      RLS + 查询自动注入   web 按权限声明渲染
        验签 + 权限点校验    （org_id 上下文驱动）  菜单与按钮
```

**组织隔离采用应用过滤与数据库防线分层设计**：

```sql
-- 数据层（兜底）：RLS 策略 + 强制启用（迁移自动为注册表中的每张 org 隔离表生成）
CREATE POLICY org_isolation ON alerts
  USING (org_id = current_setting('app.org_id')::uuid);
ALTER TABLE alerts FORCE ROW LEVEL SECURITY;
-- CI 断言：查 information_schema，有 org_id 列却无 policy 的表 = 构建失败（机器查人，不是人管机器）
```

应用层（主防线）：SQLAlchemy 事务级事件自动 `SET LOCAL app.org_id`（连接池归还不泄漏）+ ORM 自动追加 org 过滤。查询层必须显式应用组织过滤；若启用 RLS，还需验证事务上下文、连接池复用和角色绕过边界，不能仅凭策略存在就视为隔离已经生效。

**三条总线（后来者改不错的机制）**：

| 总线 | 机制 | 新开发者的接入姿势 |
|---|---|---|
| 上下文总线 | iam 中间件验签 → RequestContext{user_id, org_id, roles, permissions} 注入 | 业务代码只写 `Depends(get_ctx)`，不碰认证实现 |
| 数据访问总线 | 每个事务自动 SET LOCAL + 自动 org 过滤 | 新表只要带 org_id 列并注册，隔离自动生效 |
| 事件总线 | Redis Streams，org_id 是消息头 | 新事件带 org 头，消费者按上下文处理 |

**自举**：安装脚本创建 bootstrap admin 并打印一次性密码（对接部署篇的"安装即验收"）。内建 iam 通过标准协议（OIDC/SAML/SCIM）对接任意外部 IdP——对接的是标准，不是我们的私有实现；未来想换 Zitadel/Keycloak 做完整企业 IdP 时即插即用（方案 B 始终保留为升级路径）。

## 4. Agent 编排：图编排骨架 + 受限 LLM

海外五种路线对比后收敛的选型：

| 路线 | 代表 | 评估 |
|---|---|---|
| 自由递归推理 | Dropzone | 深，但一致性靠工程补 |
| **图编排 + 受限 LLM** | **Prophet** | "一致且确定，而不是自由形式的 LLM 链"——可靠可审计 ✅ |
| 对等单职责 agent 群 | Exaforce / Microsoft / Google | 边界清晰可分别发权 ✅ |
| 编排者+执行者 | Torq Socrates | 灵活但复杂度高 |
| 模仿人类分析师 | Radiant（已被 Cribl 收购） | — |

三方证据收敛：Prophet 用产品验证了图编排【实测】；腾讯实测单 agent 成功率仅 75%【官方文档】；学术评测 AIDA 证明**结构比模型重要**（四角色独立上下文 F1 从 0.371–0.744 拉到 0.958，去掉 Judge 掉到 0.895，9B 小模型也能跑 0.952）【论文·arXiv 2610.10608】。

我们的研判流程是一张可配置的图，LLM 只出现在边界清晰的节点里：

```
┌─────────────────────────────────────────────────────────────────┐
│                     研判流程图（图编排骨架，确定性）                  │
│                                                                 │
│  [知识前置过滤]──▶[假设生成]──▶[逐假设取证]──▶[证据级判定]──▶[聚合结论] │
│   规则/知识库      列出竞争性     图决定查什么、    每条证据独立     │
│   挡掉明确噪声     解释(受限LLM)  按实体档案组查询   verdict(受限LLM) │
│                                                                 │
│   ──▶[groundedness 门禁]──▶[三值结论 + 置信度 + Ledger]──▶[三队列]  │
│                                                                 │
│  图节点可配置；LLM 节点声明 bounded task 类型；                     │
│  复杂案件升级 → 深度调查模式（对话式：人驱动多轮、AI 执行每轮推理，全程 Ledger）│
└─────────────────────────────────────────────────────────────────┘
```

- **假设驱动**【实测·Dropzone】：先列"这条告警为什么触发的所有竞争性解释"，每个假设对应一组查询，逐一证实/排除/引出新问题——研判是科学方法不是流水线。
- **证据级 → 告警级两级判定**【实测·Intezer】：每条证据先有独立 verdict，再聚合成告警结论——可独立审计，正好喂给 groundedness 门禁。
- **Schema 语义**【论文·arXiv 2408.02442】：输出字段顺序 `evidence[] → reasoning → verdict → confidence`——JSON 模式下 GPT-3.5 有 100% 概率把 answer 排在 reason 前面，"先猜后编理由"，物理顺序能堵。
- **按岗位拆 agent**【实测·Microsoft Copilot 套件】：triage / hunt / deep-dive 三岗位，自治级别独立配置——和影子模式互补（微软按岗位发权，我们按告警类别发权）。
- **成本三道闸**【代码/官方文档】：①同 `dedup_key` 只对 leader 调 LLM、follower 复用结论②知识前置过滤（见 01 §5.2）③租户级 token 配额硬顶（阿里云"每主机每日 20 条 AI 研判"同款思路——用配额逼自己把 token 花在值得的告警上）。

## 5. AI 可靠性：六条硬约束

先接受现实水位——**当前 agent 化安全分析的真实水平是 60–75%，不是 95%**。三方独立证据：腾讯生产环境 75%【官方文档】、微软 ExCyTIn-Bench 最好模型 reward 0.606【论文】、SIABench 深度调查 40–60%（但 TP/FP 二分类 96–98%）【论文】。

| # | 约束 | 依据 |
|---|---|---|
| 1 | **三值结论**，`insufficient_info` 是一等公民（独立队列独立 SLA） | 阿里云官方即三值；火山三队列同构 |
| 2 | **工具返回三态**：`ok_empty` / `error` / `not_supported`，空结果不得作为关单依据 | ALERT-BENCH：空结果导致 4/5 方法漏掉 ≥88% 攻击告警 |
| 3 | **groundedness 门禁**：确定性实体比对（IP/hash/CVE/域名），score < 0.75 只许降级不许自动关单；门禁必须接在生产链路不只评测 | 生产执行路径必须调用门禁，CI 验证实际调用关系和失败分支 |
| 4 | **禁止同上下文自审**；要审就独立上下文或换模型 | Self-Refine 改对 16 改错 79；CoVe 改对 25 改错 132 |
| 5 | **ATT&CK 只做候选集分类**，不许开放生成 technique ID | CTIBench 开放抽取 macro-F1 仅 0.3108 |
| 6 | **处置绑定实体 + 上游原生 ID + 默认人审**，三缺一不执行 | 阿里云/火山/CrowdStrike 一致做法 |

配套：**"低慢攻击是 AI 研判的系统性盲区"**【实测·Reddit 一线评价 MS Phishing Triage Agent 为 "mid"】——这条要显式写进能力边界，`insufficient_info` 队列就是为它存在的。

## 6. 存储与检索

### 6.1 存储：大脑的工作记忆，不是数据资产

存储的角色由产品定位直接决定：SecPlexus 是外挂大脑，**原始告警的 system of record 是用户自己的 SIEM**（他们本来就有，而且存得比我们好）——我们不当第二档案馆。平台仍需保留运营闭环所必需的数据，分界线如下：

> **大脑的产出和经验永久，大脑的输入（别人的告警）只留工作窗口。**

**为什么需要持久化运营数据**。仅在收到告警时执行一次流程，无法支持后续关联、检索和审计。平台需要满足：

1. **跨厂商关联是大脑的核心职能，而它必须有地方存东西。**"EDR 说执行、防火墙说外连、身份说异常登录是同一次攻击"——这个串联只有中立层能做（厂商各自只看到自己）。告警不落地，"关联"就退化成每次研判时模型现场去各家查——这正是 01 §1.3 批评 AI 助手的原话（"同一实体 3 分钟前的相关告警要靠模型自己在会话里查"）。选不存储等于亲手把自己做回助手。
2. **经济性**。腾讯实测链路 17 万 → 1834 → 42：先归并再研判。没有预合并，10 万条/天全部进 LLM，成本差两个数量级。
3. **记忆飞轮需要历史**。机构记忆、影子模式按类别攒正确率、检出率统计，全部建立在告警历史存在之上。
4. **回写需要锚点**。处置回写用上游原生 ID，`source_refs` 必须持久；没有存储就没有案件实体，没有案件就没有审批/闭环/审计。

**保留策略（工作记忆模型）**：

| 数据 | 角色 | 保留 |
|---|---|---|
| 归一化告警 | 大脑的输入 | **工作记忆：默认 90 天滚动窗口（可配），按天分区过期自动清理**。要考古？跳回用户自己的 SIEM 查，我们保留跳转链接。案件的完整性不依赖告警行存活——证据快照自包含（见 §3.1 第 3 条） |
| raw payload | 归一化回放依据 | 7–30 天可配 |
| 事件视图 | 研判分组 | TTL 滚动，可重建（不变） |
| **案件 Case** | 大脑的产出 | **永久** |
| **调查 Ledger（含证据快照）** | 大脑的推理记录 | **永久** |
| **机构记忆 / 影子决策** | 大脑的经验 | **永久** |
| **实体档案 entities** | 大脑的知识（IP/账号/主机的画像与关系，研判上下文底座） | **永久**（画像可从新告警持续刷新） |

算账：10 万条/天 × ~1KB（raw 不进主表后）× 90 天 ≈ **9–27GB**——PG 单库时间分区绰绰有余，**冷热分层的讨论在这个模型下整体不再需要**。说明：行业均值约 3,000–4,500 条/天（04 §5.1），10 万/天是我们的设计容量——单租户峰值余量 30 倍，多源大客户也覆盖（该容量估算需在实现时通过索引、分区和真实负载验证。若未来真的规模超限——单租户 >100 万条/天或多租户 SaaS——"冷层可查但降级 + 本地缓存层"的业界全景与证据见 04 §3 备查）。

现在必须做对的三件事（否则以后要重写）：

1. **raw 永不进主表**——主表只放 `raw_uri` + `raw_hash`，单行从 5–50KB 降到 ~1KB
2. **查询接口可路由**——语义层字段 → 后端 SQL 的编译层，不散落裸 SQL
3. **狩猎从第一天就是异步的**——`POST /hunt → 轮询`，即使现在只要 200ms

### 6.2 检索：不自研发语言

三家国内厂商（阿里 SPL、腾讯 CQL、火山检索语法）全部收敛到同一个结构：**`过滤条件 | SQL`**——过滤用索引，聚合用 SQL-92，管道符连接【官方文档；火山部分基于搜索摘要，见 04 §8】。这个形态用户已有肌肉记忆。

```
@actor.user.name = "alice" AND @severity_id >= 3 | SELECT count(*) GROUP BY src_endpoint.ip
└──────────────── 过滤表达式（编译成 WHERE）──────┘   └────── SQL 片段（AST 校验透传）─────┘
```

查询执行层要求单条 SELECT、表白名单、AST 级组织过滤和行数上限，不能仅依赖调用参数自报组织。模型查询契约还需满足：**模型拿到的 schema 里根本没有任何字段能携带 SQL/SPL/自由文本**，CI 断言 schema 而不是断言代码——"schema 才是真正约束模型的东西"。

## 7. 两个共享库（不是服务）

| 库 | 内容 | 为什么是库 |
|---|---|---|
| `contracts` | OCSF 模型、枚举、API 契约、查询 IR、RequestContext——**一个 Python 包直接 import，天然单一事实源**（单语言最大红利：零跨语言生成设施） | 全部角色共用，服务化只有网络开销和版本漂移 |
| `connectors` | 厂商连接器 + 归一化 profile + 回归样本 | 只被 collector 引用，独立版本化 |
| `orchestrator` | workflow 引擎：**10 类节点**（python/tool/llm/http/branch/loop/parallel/wait/approval + subworkflow）、持久化审批暂停、幂等键、Python 节点子进程隔离 | correlator/agent/soar 复用；长时间运行的 Python 节点需评估内存与故障隔离；处置动作（block_ip/isolate_host 等）不是节点类型，是 tool 节点调用的工具——否则每接一个厂商就要改引擎 |
| `audit` | 追加式哈希链审计 | 审计必须内嵌在每个写入点，不能是旁路服务 |

## 9. 工程标准（每个组件强制，CI 检查）

| # | 标准 | 条款 |
|---|---|---|
| 1 | **队列消费语义** | 至少一次投递 + 消费幂等键 + 指数退避重试 + DLQ 死信——写死为事件总线协议，不是各消费者自己发挥 |
| 2 | **可观测** | **structlog** 结构化日志 + **OpenTelemetry 全链路 trace**：请求 → 队列 → 工具调用 → LLM 调用（每次 LLM 调用一个 span，模型/耗时/token 直接可见） |
| 3 | **健康检查与优雅停机** | 每个角色强制 `/healthz` `/readyz`；SIGTERM 优雅排水（处理完在途消息再退）；K8s preStop 对齐 |
| 4 | **RLS 自动断言** | org 隔离表集中注册，迁移自动建 policy；CI 查 information_schema——有 org_id 列却无 policy 的表 = 构建失败（机器查人，不是人管机器） |
| 5 | **声明式种子** | 预置角色矩阵等种子数据是代码常量，启动幂等同步（不许手改库） |
| 6 | **错误码注册表** | 错误码集中定义一处，API 文档自动带出；禁止散落字符串 |
| 7 | **数据库迁移** | Alembic 迁移单侧持有，迁移文件即版本历史 |
| 8 | **设计原则** | **正确性由机器保证，不靠人的记忆**：policy 自动建、种子自动同步、隔离自动断言——一切"手动维护/人肉纪律"的方案不进入本系统 |

> 注：Go 方案曾要求的 proto/OpenAPI 三端生成与 gen/ 零手改校验，在单语言下**天然不需要**——contracts 共享包就是单一事实源，这是回归 Python 全栈的最大复杂度削减。
