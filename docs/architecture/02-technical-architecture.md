# 02 · 技术架构

> 用大白话说：9 个自研服务 + 4 个开源组件跑在 PostgreSQL 和 Redis 上。数据从左边流进来（告警 + AI 流量两条入口），经过归并降噪变成告警和事件视图，AI 在图编排的骨架里研判，人批了以后 SOAR 执行处置回写回原系统。存储只上一个 PG（量级算过账），检索不自研发语言。

## 1. 服务清单与拆分理由

服务拆分的判据不是"功能不同"，而是以下五条之一：**独立扩容**（瓶颈维度不同）、**故障隔离**（会卡住会崩溃）、**独立变更**（改动频率不同）、**技术栈强制**、**安全边界**（高危能力单独管控）。

### 1.1 v1 全景（自研 9 + 开源 4 = 13 个容器）

| # | 服务 | 类型 | 语言 | 职责 | 为什么拆 |
|---|---|---|---|---|---|
| 1 | `collector` | 自研 | Python | 一切外部数据的唯一入口：告警接入、形状判别、OCSF 归一化、L0/L1 校验 | 改动最频繁（每接一家厂商就改），独立发版；突发流量独立扛 |
| 2 | `correlator` | 自研 | Python | D1 去重 → D2 窗口折叠 → D3 跨源关联 → 告警 + 事件视图（攻击链） | 吞吐瓶颈，纯 CPU，按 `tenant:entity` 分区保序扩容 |
| 3 | `agent-runtime` | 自研 | Python（内嵌 LiteLLM SDK） | 全部离线 AI 推理的宿主：研判 Agent（图编排骨架）、workflow 引擎、NL→查询 | **LLM 有 1/4 概率超时/无结果**【官方文档·腾讯实测】，必须和管线故障隔离 |
| 4 | `soar` | 自研 | Python | 预案库、审批状态机（持久化暂停）、高危动作执行、按上游原生 ID 回写；**通知（邮件/IM webhook/工单）是它的 governed action** | 安全边界：Agent 提议 / SOAR 执行的权限分界 |
| 5 | `ai-policy` | 自研 | Python（内嵌 NeMo Guardrails 库） | AI 安全策略大脑：规则、检测、ext_authz 决策、事件回流、管理 API | 策略与决策独立演进，不耦合网关数据面 |
| 6 | `iam` | 自研 | Python | 登录、SSO（OIDC/SAML）、RBAC/ABAC、多租户、API Token、SCIM | 身份是核心攻击面，被所有服务验签 |
| 7 | `console` | 自研 | Python / FastAPI | 查询（热层同步/狩猎异步）、Case、三队列工作台、SSE、资产与连接器配置 | 长尾查询 + 高危操作边界 |
| 8 | `web` | 自研 | TypeScript / Next.js | 前端 | 技术栈强制 |
| 9 | `scheduler` | 自研 | Python | 全部定时任务的唯一入口 | 定时任务集中管理，不散落各服务 |
| 10 | `ai-gateway` | **开源** | agentgateway（Rust） | 哑数据面：用户 AI 流量（LLM+MCP）的 inline 治理，决策回调 #5 | 只依赖 xDS + ext_authz 两个稳定协议，升级不被绑定 |
| 11 | `postgres` | **开源** | PostgreSQL 16 | 主存储 | — |
| 12 | `redis` | **开源** | Redis 7 | 队列（Streams）、去重窗口、限流 | 去重要带 TTL 的高频读写 |
| 13 | `object-storage` | **开源** | MinIO / S3 兼容 / 本地 FS | raw payload、Parquet 归档 | raw 永不进主表 |

**两个容易混淆的区分**：`ai-gateway` 管的是**用户**的 AI 流量（防护对象），agent-runtime 内嵌的 LiteLLM SDK 管**我们自己**调模型的流量（内部出口）——方向相反不能共用；`soar` 与 `agent-runtime` 的分界是"想"和"做"——高危动作不能跑在 AI 进程里。

**语言选择的依据**【代码·AiSOC 实测】：AiSOC 的 ingest 用 Go（16k 行），业务面全 Python（api 140k 行）。我们算过账：10 万条/天 = 1.16 条/秒，峰值按 100 倍算 Python asyncio + 批量写绰绰有余；归一化是改动最频繁的代码，Python 的迭代速度比 Go 的编译周期值钱。唯一例外：用户有 syslog UDP 高频推送时，加一个纯收包的 Go thin gateway（只收包写队列，不解析）。

```
   scheduler ──定时──▶ ① API 拉取 · ③ 定时任务 · 蜜标/情报/扫描
```

三条设计要点：

1. **两条数据源的汇合点在 ①**——`ai-policy` 拦下的注入事件回流 `collector`，从此和 EDR 告警走完全相同的链路。"防护对象 = 运营对象"在架构上就这一条线。
2. **跨阶段连接全靠队列不靠调用**——①→② 走 Redis Stream，②→③ 走 Case 事件；任何一级慢了或挂了，上游照常摄入，恢复后接着跑。
3. **`worker` 和 `agent` 必须分进程不是洁癖**——LLM 卡住会阻塞去重；且两者扩容维度完全不同（CPU 密集 vs 网络等待密集）。

## 3. 数据模型

### 3.1 核心实体

```
assets            资产（含 AI 资产）+ 指纹；关键性等级（处置门控用）
alerts            告警：OCSF 2004 结构 + 实体抽取 + ATT&CK + chain 元数据
                  + source_refs[]（上游原生 ID 映射，一对多）
                  + aggregation_evidence（上游合并探测三档置信）
incident_views    事件视图：Redis 滚动 TTL（不建重表）+ 告警上的 chain 字段
cases             案件（OCSF 2005）：状态机 + case_tasks + case_timeline
investigations    调查 Ledger：Run / Event / Artifact（prompt、工具调用、引用全量）
institutional_memory  机构记忆：结论沉淀 + 分析师纠正（reason 必填）+ 用户直录
rule_proposals    规则建议：propose → review → eval-gated → promote
shadow_decisions  影子模式记录：从第一天攒，授权的依据
entities          实体档案（IP/账号/主机/hash）：画像、历史、关系（agent 的上下文底座）
```

**两条贯穿性设计**：

1. **`tenant_id` 进所有业务表的主键/唯一键**。这是"架构上支持未来多集群"的真正含义——不是现在就上多集群，而是现在不做未来拆不动的事：届时无论逻辑复制按租户拆分还是 hash 分片，都不用改表结构。
2. **保留策略分级**：归一化告警永久（可归档冷存）、raw payload 7–30 天可配（归一化回放与合规的依据，过期自动清）、调查 Ledger 与影子决策永久（审计要求）、事件视图 TTL 滚动（可重建，不持久）。

### 3.2 归一化：OCSF 2004，不追全量映射

**【官方文档】** OCSF v1.9.0（当前稳定版）2024-11 捐给 Linux Foundation，2026-06 成为 ITU 国际标准；`security_finding`(2001) **已废弃**（since 1.1.0），新项目直接用 `detection_finding`(**2004**)。

四个必抄的机制【官方文档·OCSF 2004 定义】：

| 机制 | 作用 |
|---|---|
| `count` + `start_time`/`end_time` | 上游聚合语义的唯一标准字段——**必须读进内部模型**（AiSOC 的归一化器把上游 count 整个吃掉，是反面教材【代码】） |
| `unmapped` | 映射不上的字段全塞这里，一条不丢——半年后排障的救命稻草 |
| `vendor_attributes` | "厂商给的值"和"我改过的值"分开存——可解释 AI 的刚需 |
| `observables[]` + `evidences[]` | 实体集中列出带路径引用，关联/富化/情报都从这里读 |

归一化分四层：**L0 最小必需集**（缺了进隔离区不进主表）→ **L1 通用实体**（actor/user/process/file/network + ATT&CK ID）→ L2 厂商专属（按需）→ L3 raw 永存。工作量比例约 7:2.5:0.5。

**六条从真实代码缺陷提炼的工程铁律**（每条都有 AiSOC/flocks 的实证，明细见 04 §4）：

1. 时间解析失败 → `null` + warning，**绝不回退 `now()`**（AiSOC `normalizer.go:1063` 的真实缺陷）
2. 缺失就是 `null`，不写 `"none"` 哨兵值
3. 解码顺序 UTF-8 strict → GB18030 → replace，**编码记在事件上**（国内设备大量 GBK）
4. `actor.kind` / `outcome` 判断不出就是 `unknown`，不许猜
5. 字段路径支持数组下标 + **填充率报表**（映射静默失效是常态）
6. 归一化质量门禁进 CI：填充率、warning 计数看板、schema 校验、每连接器 5–10 条回归样本

### 3.3 降噪合并：三层独立可解释

厂商合并解决"别刷屏"（单产品、单规则、同实体）；我们的合并解决"研判对象唯一"（跨产品、跨厂商、跨时间）。分层是因为混在一起就永远回答不了"这两条为什么被合并了"——用户和分析师一定会问。

| 层 | 干什么 | 键 | 输出 |
|---|---|---|---|
| D1 精确去重 | 重复投递（重放/重试/多路采集） | 同源 + external_id + 关键字段 hash | 丢弃，计数 +1 |
| D2 同源窗口抑制 | 同规则对同实体反复刷 | 同源 + rule + 主实体 + 时间窗（5–60min） | 折叠，保留 count 和时间范围 |
| D3 跨源实体关联 | 多产品告警串成一个事件 | 共享实体（IP/账号/主机/hash/域名）≥2 | 事件视图 + 关联理由（必须可解释、可一键拆开） |

**上游是否已合并判断不出来**——查遍 OCSF/ECS/ASIM/UDM/ASFF/Sentinel/QRadar 没有任何标准有 `is_aggregated` 字段【官方文档】。落地方式是接入期"合并指纹探测"报告（计数字段、ID 稳定性、时间戳对齐痕迹、上层对象 ID 七项探测），输出**三档置信度**而非布尔值：已确认聚合 / 疑似聚合 / 未观察到迹象（≠未聚合）。

**分区保序**【代码·AiSOC ADR-0012 的教训】：队列分区键必须 `tenant:entity`，且 entity 解析顺序必须与关联键**同一份代码**——否则同一实体的告警散在不同分区被不同副本消费，序列拼错、事件一分为二，而且看起来一切正常。无实体事件回退 event_id（回退 tenant_id 会造成热分区）。

## 4. Agent 编排：图编排骨架 + 受限 LLM

海外五种路线对比后收敛的选型：

| 路线 | 代表 | 评估 |
|---|---|---|
| 自由递归推理 | Dropzone | 深，但一致性靠工程补 |
| **图编排 + 受限 LLM** | **Prophet** | "一致且确定，而不是自由形式的 LLM 链"——可靠可审计 ✅ |
| 对等单职责 agent 群 | Exaforce / Microsoft / Google | 边界清晰可分别发权 ✅ |
| 编排者+执行者 | Torq Socrates | 灵活但复杂度高 |
| 模仿人类分析师 | Radiant（已被 Cribl 收购） | — |

三方证据收敛：Prophet 用产品验证了图编排【实测】；腾讯实测单 agent 成功率仅 75%【官方文档】；学术评测 AIDA 证明**结构比模型重要**（四角色独立上下文 F1 从 0.371–0.744 拉到 0.958，去掉 Judge 掉到 0.895，9B 小模型也能跑 0.952）【论文·arXiv 2610.10608】。

我们的研判流程是一张可配置的图，LLM 只出现在边界清晰的节点里：

```
┌─────────────────────────────────────────────────────────────────┐
│                     研判流程图（图编排骨架，确定性）                  │
│                                                                 │
│  [知识前置过滤]──▶[假设生成]──▶[逐假设取证]──▶[证据级判定]──▶[聚合结论] │
│   规则/知识库      列出竞争性     图决定查什么、    每条证据独立     │
│   挡掉明确噪声     解释(受限LLM)  按实体档案组查询   verdict(受限LLM) │
│                                                                 │
│   ──▶[groundedness 门禁]──▶[三值结论 + 置信度 + Ledger]──▶[三队列]  │
│                                                                 │
│  图节点可配置；LLM 节点声明 bounded task 类型；                     │
│  复杂案件升级 → 深度调查模式（对话式自由推理，全程 Ledger）            │
└─────────────────────────────────────────────────────────────────┘
```

- **假设驱动**【实测·Dropzone】：先列"这条告警为什么触发的所有竞争性解释"，每个假设对应一组查询，逐一证实/排除/引出新问题——研判是科学方法不是流水线。
- **证据级 → 告警级两级判定**【实测·Intezer】：每条证据先有独立 verdict，再聚合成告警结论——可独立审计，正好喂给 groundedness 门禁。
- **Schema 语义**【论文·arXiv 2408.02442】：输出字段顺序 `evidence[] → reasoning → verdict → confidence`——JSON 模式下 GPT-3.5 有 100% 概率把 answer 排在 reason 前面，"先猜后编理由"，物理顺序能堵。
- **按岗位拆 agent**【实测·Microsoft Copilot 套件】：triage / hunt / deep-dive 三岗位，自治级别独立配置——和影子模式互补（微软按岗位发权，我们按告警类别发权）。
- **成本三道闸**【代码/官方文档】：①同 `dedup_key` 只对 leader 调 LLM、follower 复用结论（flocks 实证）②知识前置过滤（见 01 §5.2）③租户级 token 配额硬顶（阿里云"每主机每日 20 条 AI 研判"同款思路——用配额逼自己把 token 花在值得的告警上）。

## 5. AI 可靠性：六条硬约束

先接受现实水位——**当前 agent 化安全分析的真实水平是 60–75%，不是 95%**。三方独立证据：腾讯生产环境 75%【官方文档】、微软 ExCyTIn-Bench 最好模型 reward 0.606【论文】、SIABench 深度调查 40–60%（但 TP/FP 二分类 96–98%）【论文】。

| # | 约束 | 依据 |
|---|---|---|
| 1 | **三值结论**，`insufficient_info` 是一等公民（独立队列独立 SLA） | 阿里云官方即三值；火山三队列同构 |
| 2 | **工具返回三态**：`ok_empty` / `error` / `not_supported`，空结果不得作为关单依据 | ALERT-BENCH：空结果导致 4/5 方法漏掉 ≥88% 攻击告警 |
| 3 | **groundedness 门禁**：确定性实体比对（IP/hash/CVE/域名），score < 0.75 只许降级不许自动关单；门禁必须接在生产链路不只评测 | AiSOC 真实缺陷：scorer 当过"只有评测没有调用方"的摆设，自信误报被自动关单 |
| 4 | **禁止同上下文自审**；要审就独立上下文或换模型 | Self-Refine 改对 16 改错 79；CoVe 改对 25 改错 132 |
| 5 | **ATT&CK 只做候选集分类**，不许开放生成 technique ID | CTIBench 开放抽取 macro-F1 仅 0.3108 |
| 6 | **处置绑定实体 + 上游原生 ID + 默认人审**，三缺一不执行 | 阿里云/火山/CrowdStrike 一致做法 |

配套：**"低慢攻击是 AI 研判的系统性盲区"**【实测·Reddit 一线评价 MS Phishing Triage Agent 为 "mid"】——这条要显式写进能力边界，`insufficient_info` 队列就是为它存在的。

## 6. 存储与检索

### 6.1 存储：v1 一个 PG 就够，是算出来的

10 万条告警/天 × 3KB = 300MB/天 → **110GB/年**。这个量级 PG 单库 + 时间分区轻松扛住，冷热分层是伪需求。三条业界证据支撑"轻"：flocks 用 SQLite 都在跑【代码】；IBM QRadar 的 offense 也存 PostgreSQL【官方文档】；AiSOC ADR-0005 明确**拒绝引入第二个热分析引擎**（"多一个引擎 = 多一套备份/权限隔离/容量规划，运维翻倍收益不明"）【代码】。

现在必须做对的三件事（否则以后要重写）：

1. **raw 永不进主表**——主表只放 `raw_uri` + `raw_hash`，单行从 5–50KB 降到 ~1KB
2. **查询接口可路由**——语义层字段 → 后端 SQL 的编译层，不散落裸 SQL
3. **狩猎从第一天就是异步的**——`POST /hunt → 轮询`，即使现在只要 200ms

真到分层的触发条件（单租户 >100 万条/天 / 接了原始日志 / 多租户 SaaS）再上"冷层可查但降级 + 本地缓存层"——Elastic 的 searchable snapshots benchmark（105TB/90 天：frozen 未缓存 p99.9 = 2.3–13s，已缓存 1–11s，最差首查 5 分钟）证明**没有缓存的冷查询是灾难，有缓存接近热层**【官方文档·Elastic】。跨冷热业界全景对照表见 04 §3。

### 6.2 检索：不自研发语言

三家国内厂商（阿里 SPL、腾讯 CQL、火山检索语法）全部收敛到同一个结构：**`过滤条件 | SQL`**——过滤用索引，聚合用 SQL-92，管道符连接【官方文档】。这个形态用户已有肌肉记忆。

```
@actor.user.name = "alice" AND @severity_id >= 3 | SELECT count(*) GROUP BY src_endpoint.ip
└──────────────── 过滤表达式（编译成 WHERE）──────┘   └────── SQL 片段（AST 校验透传）─────┘
```

执行层的安全约束直接抄 AiSOC `lake_sql.py`【代码】：单条 SELECT、表白名单、AST 级强制注入 tenant_id（不是参数级）、行数上限 100k。更硬的一条纪律抄自它的 `hunt/plan.py`：**模型拿到的 schema 里根本没有任何字段能携带 SQL/SPL/自由文本**，CI 断言 schema 而不是断言代码——"schema 才是真正约束模型的东西"。

## 7. 两个共享库（不是服务）

| 库 | 内容 | 为什么是库 |
|---|---|---|
| `contracts` | OCSF 模型、枚举、API 契约、查询 IR | 9 个进程共用，服务化只有网络开销和版本漂移 |
| `connectors` | 厂商连接器 + 归一化 profile + 回归样本 | 只被 collector 引用，独立版本化 |
| `orchestrator` | workflow 引擎：**10 类节点**（python/tool/llm/http/branch/loop/parallel/wait/approval + subworkflow；flocks 8 类实证，wait/parallel/approval 补自 AiSOC 的 25 步 playbook）、持久化审批暂停、幂等键、Python 节点子进程隔离 | correlator/agent/soar 复用；flocks 证明 Python 节点会内存泄漏，子进程隔离必须预留；处置动作（block_ip/isolate_host 等）不是节点类型，是 tool 节点调用的工具——否则每接一个厂商就要改引擎 |
| `audit` | 追加式哈希链审计 | 审计必须内嵌在每个写入点，不能是旁路服务 |

## 8. 与参照实现的规模对照
