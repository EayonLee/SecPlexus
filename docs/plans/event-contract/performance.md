# Event 接入、发布与存储的性能验收

本计划覆盖设备报文进入 Ingest，直至标准 Event 可在 ClickHouse 中按条件查回。先治理接收端的内存和连接生命周期，再评估新契约带来的成本。Kafka 确认与 ClickHouse 可查询是两个独立的完成点，各自记录吞吐、延迟和故障窗口。

## 已落地的运行边界

HTTP 并发处理的设备请求数、单包字节与逻辑消息数分别限额，短暂饱和返回 503 与重试提示。解析队列同时按消息数和输入字节限额。提交者只在登记时短暂持有锁，读包、解析和网络重试均在锁外。Syslog 停用会关闭监听与已建立的连接。平台 Kafka 故障时继续保留待确认批次，达到进程排空期限时停止重试并记录丢弃量。Kafka 拉取分批发布并提交已确认的位移，超时交回分区并等待下次配置刷新。完整输出正文内存和 Kafka 客户端总缓冲仍需实测定界，部分确认后整批重试仍存在重复窗口。

## 容量依据

既有单机目标是持续 50,000 EPS。历史抽测采用 8 个逻辑核、16 GiB、单节点 Kafka、每个 HTTP 请求 1,000 条短 JSON。30.03 秒内受理 1,488,508 条，Kafka 确认相同数量，约 49,567 条/秒，接收到 Kafka 确认 P99 为 447 ms。相对计划输入少受理 11,492 条，队列最高 10,000。放大这个数字不能得出混合报文的日容量。[历史压测记录](../ingest-closeout/plan.md)

2026-11-26 在 Apple M1 Pro 上复跑现有规则微基准，三轮 CEF 为 3.37–3.63 µs/条、4,097 B/条、52 次分配，JSON 为 2.30–2.75 µs/条、2,939 B/条、33 次分配。以这份 CEF 样本持续 50,000 EPS 估算，仅解析映射每秒累计分配约 205 MB。这个数反映 GC 需要处理的分配流量；进程常驻内存还取决于对象的存活时间。新增字段类型、枚举和条件校验时，用相同样本比较，再覆盖完整事件构造、序列化和发布。[基准样本与执行范围](../../../src/apps/ingest/internal/normalizer/bench_test.go)

部署前从代表性业务窗口取得以下输入，并保存到该部署的容量记录中。

| 输入 | 用途 |
|---|---|
| 日事件数、每秒和每分钟的峰值、峰值持续时间，各协议与来源占比 | 日均 EPS = 日事件数 / 86,400。持续 50,000 EPS 等于 43.2 亿条/日。用观测峰值和增长预算选压测负载；单列某个来源突发时其他来源的延迟。 |
| 报文与标准 Event 的平均、P95、P99 和最大字节数，规则与单批消息分布 | 分别算输入、发布、写入字节率；记录解码展开、未映射字段以及失败流的开销。用峰值字节率和并发数核算缓冲。默认 10,000 个队列槽位在每秒新增 50,000 条且暂停消费时仅能容纳 0.2 秒。 |
| Kafka 保留窗口、累计保存天数、压缩后字节/条、副本数、可用磁盘 | 两套存储分别核算。CK 基础盘量 = 日事件数 × 实测压缩后字节/条 × 天数 × 副本数。另留合并、迟到数据、回填和备份作业的空间。Kafka 空间按各 topic 的压缩后写入速率、保留窗口和副本数估算。 |
| 最长可容忍中断、在线查询组合、恢复时可用写入速率 | 追赶秒数 = 积压条数 /（实测恢复写速 − 同期到达速率），分母须为正。单独检查积压最重的分区，确认最早未消费记录能保留到追赶完成。 |

## 从现有代码确定的整改顺序

| 优先级与边界 | 现状与后果 | 实施动作和验收证据 |
|---|---|---|
| 1 · Syslog 连接回收 | 每条已接受的 TCP 连接占用一个 goroutine。在停用或换端口时，binding 关闭 UDP 套接字和 TCP 监听器；已接受连接的读取循环仍可停在阻塞的 Read，直至对端关闭或读取出错。现有停用测试只验证端口可再次绑定。[连接实现](../../../src/apps/ingest/internal/channel/syslogchannel/channel.go) · [现有测试](../../../src/apps/ingest/internal/channel/syslogchannel/disable_test.go) | 由 binding 持有并关闭自己接纳的连接，处理关闭与 Accept 同时完成的情况，锁外等待读取协程退出。以已收过一条消息的空闲连接验证停用、换端口和进程排空；旧连接结束、新绑定正常、其他接入点维持可用。反复启停后按接入点核对活动连接、文件描述符及 goroutine 堆栈。 |
| 1 · HTTP 和流水线内存 | HTTP 先读完整请求体，拆出全部逻辑消息后才检查条数上限。普通按行切片还可因个别排队消息引用整个请求体。解析队列按条数限流；多个并发请求、已序列化批次和客户端发送缓冲可同时驻留。[HTTP 入口](../../../src/apps/ingest/internal/channel/httpchannel/handler.go) · [分行](../../../src/apps/ingest/internal/parser/split.go) · [流水线](../../../src/apps/ingest/internal/pipeline/pipeline.go) | 限制并发读取的总字节预算；拆包达到条数上限时及早结束，保留超限和非法整包在受理前拒绝的语义。为队列与发布批次核算实际保留字节，明确底层字节数组归属；按实测选择复制小片段或按请求持有预算至最后一条释放。覆盖 JSON 数组、NDJSON、空行、多行规则、取消及部分受理。比较峰值 RSS、GC 后存活堆和分配，核对 accepted/rejected。 |
| 1 · 发布阻塞与停机 | HTTP/Syslog 共用的批处理器同步发布，失败会阻塞后续批次。当前排空预算在每批发布失败后单独起算，退避 Sleep 不能被关停唤醒。worker 可阻塞在投递已解析事件，进程总退出时间可能累加多个批次。批次切片缩为零仍保留旧槽位对正文的引用，直至覆盖。[批处理与退出实现](../../../src/apps/ingest/internal/pipeline/pipeline.go) | 用同一个进程排空截止时间约束在途发送、等待及退避；释放已发批次的正文引用。验证满队列且 broker 持续慢或不可用时，入口停止受理，已确认、仍待重放和已丢弃的条数可核对，在部署宽限内退出。另覆盖 Flush 等待者取消及与关闭并发；目前 Flush 主要由测试调用。将阻塞栈与进度计数一起采集，区分正常背压、过长等待和死锁。 |
| 1 · Kafka 拉取、发布与身份 | 每个接入点独立拉取，整批输入与解析产物共存直至发布确认；这条路径绕过 HTTP/Syslog 队列。发布器只向上返回整批首个错误；若部分记录已确认，整批重试可能重复。输出确认后、输入位移提交前重启，源记录再解析会使用新的进程序号和 epoch。[拉取与提交](../../../src/apps/ingest/internal/channel/kafkachannel/consumer.go) · [发布结果](../../../src/apps/ingest/internal/publish/kafka.go) · [事件构造](../../../src/apps/ingest/internal/pipeline/pipeline.go) | 按活跃接入点总数预算客户端预取和解码批次，按字节与条数分批。分区仅推进已确认的连续位移，验证部分成功、重平衡、取消和永久失败记录的处置。保留同键顺序；分别验证“重放同一标准 Event”与“重新拉取同一源记录”。后者若要求同一身份，先定义稳定来源标识与 topic、分区、位移的作用域，禁止仅按原文字节合并独立观测。[Kafka 交付语义](https://kafka.apache.org/41/design/design/) |
| 2 · 事件模型与规则 | 规则应用后还需组装嵌套对象和序列化。全量配置刷新会逐个接入点编译规则，多个接入点共享一条规则时重复工作。[正文组装](../../../src/apps/ingest/internal/pipeline/pipeline.go) · [规则加载](../../../src/apps/ingest/internal/repository/input_loader.go) | 在加载或编译时解析契约路径、字段类型与枚举约束，运行时只验证本条记录的适用条件。先在同一配置快照内共享规则 ID、规则修订及契约版本均相同的不可变编译结果；旧快照随在途记录释放，刷新失败沿用上次成功配置。比较共享一条规则与各用一条规则时的刷新耗时、GC 峰值和数据面 P99。 |
| 2 · PostgreSQL、Redis 与观测 | PG 提供配置快照；HTTP 的 Redis 令牌桶每个通过鉴权及媒体类型检查的请求消耗一个配额，并设置过期时间。同样 EPS 下，单条推送与千条一批的 Redis 操作量可相差三个数量级。按接入点抓取指标也会生成统计快照。[限流](../../../src/apps/ingest/internal/channel/httpchannel/limiter.go) · [指标快照](../../../src/apps/ingest/internal/pipeline/pipeline.go) | 在隔离环境复现共享 PG、Redis 的部署拓扑，在流量峰值同时保存规则、读取配置、抓取指标并请求 IAM。记录 PG 连接池等待和锁等待、Redis 延迟和超时、管理请求 P99。保持规则和字段目录在内存读取。按来源变更与监控抓取频率检查序列基数和快照成本；日志按有界原因聚合，事件 ID 用于个案排查。 |

## ClickHouse 写入与查询

事件写入消费组按条数、累计字节和最长等待时间中最先达到的条件提交一批。记录批次实际分布与每批涉及的月份分区，按部署配置确认写入持久性后才提交 Kafka 连续位移。写入未确认时保留重放位置。实测应涵盖跨月迟到、写成功但确认丢失、积压恢复与在线查询同时发生。批量写入可减少小 part 和后台合并工作，实际批大小由写延迟、part 增长速度及内存预算共同确定。[ClickHouse 批量写入](https://clickhouse.com/docs/optimize/bulk-inserts) · [表结构与重放语义](storage.md)

用同一份时间与来源分布测试三类查询：按时间和类别筛选、跨类别查源或目的 IP、按事件 ID 和证据时间回查。常用检索走类型列，仅详情读取完整正文。记录 P95/P99、扫描行和字节、峰值内存、压缩后字节/条、每分区活动 part 与合并积压。对重复写入，在后台合并前后分别验证准确计数及其代价。只有查询超过本部署预算且执行计划能定位瓶颈时，再评估排序键、投影或索引，并一并测量写放大和存储成本。

## 实施验收与发布

| 阶段 | 方法 | 通过条件 |
|---|---|---|
| 建立基线 | 固定提交、Go/依赖版本、CPU 配额、内存限制、分区、副本、压缩及网络。脱敏样本覆盖真实占比的短 JSON、CEF、长记录、字段展开、解析失败和慢源。开跑前登记各段延迟、可容忍拒收及恢复窗口。用独立发压端按目标速率发送并记录实际发出量。 | 同一数据集和硬件可复跑，报告含实际 mix、事件/秒和字节/秒。HTTP 按请求、消息分开计数，UDP 以发送端序号对照内核与应用的丢包记录。 |
| 稳态与峰值 | 先预热，再按真实流量结构持续测试。建议第一轮稳态 60 分钟，另以短时峰值并发读写、刷新配置；在容量评估环境做 8 小时长稳，若部署有明显日周期再覆盖全天。 | 目标速率下受理、标准流、诊断流与 Kafka 实收能对账，区分受理前拒绝、受理后丢弃、重复和期末在途。持续 5 万 EPS 的结论须单独列实收、拒收、P99 与积压趋势。归档上线后增加 CK 可查吞吐、端到端延迟及去重后的计数。 |
| 资源生命周期 | 在相同负载和暂停入流、排空后的相同时点采集 GC 后存活堆、RSS、goroutine 栈、打开文件数、连接池占用与在途字节。分别做连接启停、规则替换及消费者重连。用 heap 比较存活对象，用 block/mutex profile 和 goroutine 栈定位等待。诊断采样限于受控运行环境。[Go 性能诊断](https://go.dev/doc/diagnostics) | 资源在配置预算内形成稳定区间；负载和活跃接入点恢复相同后，多轮循环无持续增长的对象、连接或同类等待栈。对线性增长或长期无进度保留前后样本、对象所有者和复现条件；用对应生命周期回归验证修复。 |
| 故障、追赶与升级 | 分别让平台 Kafka 与事件存储 ClickHouse 短时不可用，保留入流，恢复后测积压斜率；在线迁移或重启时核对每分区位移。滚动升级核算新旧实例并存时的连接和缓冲，记录 SIGTERM 至退出耗时。 | 稳态请求不会因单个故障无限占用内存或连接；故障期间的拒收、重放、重复及缺口可解释。恢复后在约定窗口追平，排空在退出宽限内完成。超过保留期的缺口按分区记录。 |

本轮运行了 pipeline 与 normalizer 的现有竞态测试，均通过。Go 竞态检测覆盖实际执行到的并发内存访问。连接泄漏、死锁、持续吞吐和 CK 追赶分别由上表的生命周期、无进度诊断、长稳与故障演练验收。本轮尚无这些实测结果。昂贵的混合负载与长稳测试使用专用容量环境，日常变更按受影响路径复用微基准、回归与真实组件集成测试。[Go 竞态检测](https://go.dev/doc/articles/race_detector) · [项目测试分层](../../development/testing.md)
