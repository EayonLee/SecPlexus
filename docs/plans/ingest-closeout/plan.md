# 实施与验收

依据 [spec.md](spec.md) 和[测试分层判定表](../../development/testing.md)。记录每批改动对应的失败用例、验证命令、结果和剩余项。

| 顺序 | 工作 | 完成判据 |
| --- | --- | --- |
| 1 | 模块 README、既有用例盘点、四服务基线 | README 与现有路由、配置一致；列出已覆盖、需扩充和环境缺口。 |
| 2 | 三协议接入表单、轮换、解绑、删除确认 | 用现有 HTTP E2E 扩充一次令牌轮换和权限检查；Kafka 必填与载荷边界放在低层，真实 Kafka 路径复用通道集成。 |
| 3 | 试算响应、映射表单、向导和诊断 | 真实 API 返回有效 OCSF 预览和失败结果，页面展示同一结果；向导不可用旧试算结果提交。接入点诊断有真实计数并正确处理空数据。 |
| 4 | FortiGate CEF 映射 | 使用公开字段定义编写一项流量映射；测试代表样本的 OCSF 输出，并验证可选用、复制及内置规则的写入限制。 |
| 5 | 审计可靠性 | 用真实 PostgreSQL/IAM 验证业务写入与待投递事实一起提交、失败恢复后沿用入队时间且只有一条审计。以 Ingest 事务为边界，IAM 接收端按事件 ID 去重。 |
| 6 | Kafka 集成门禁、fuzz、容量验收 | 隔离 broker 实际执行位移与顺序用例；定时 fuzz 有时限；记录持续压测观察值和结论。 |
| 7 | 全栈与浏览器验收、文档同步 | 真实 Web/IAM/Ingest/Console 回归，覆盖匿名、只读和可写边界；检查桌面和窄屏、中英文、两种主题、空态、错误、确认与组件一致性，修正发现后重验。 |

## 依赖与范围

- 步骤 2 可在既有管理 API 上交付。步骤 3 的样本结果使用运行时相同的解析逻辑，诊断使用现有指标能提供的证据。步骤 4 依赖统一映射契约。步骤 5 独立验证失败、重试与去重。步骤 6 和步骤 7 使用独立数据库、Redis 测试资源、Kafka topic 和消费组。
- 旧接口迁移的两阶段部署要求因合并为基线而关闭。协议专属 JSON 校验依据现有用例层契约。可信代理设置只有新功能需要来源地址时才引入。
- 本计划覆盖接入与现有服务联调；告警关联、模型调用、案件与真实工作台属于后续平台模块。

## 验证入口

```sh
make test
make integration ARGS="--docker"
make test-e2e ARGS="--docker"
make typecheck
make lint
make catalogs
```

浏览器以相同的隔离栈完成实际操作，逐项记录数据写入与 Kafka 结果。容量验收在有明确资源隔离的环境执行，凭据、私有样本和环境地址不进入仓库。

## 现有覆盖与缺口

| 路径 | 复用的覆盖 | 需要补齐 |
| --- | --- | --- |
| Web → IAM、Console | 登录、CSRF、角色权限、跨标签撤销、审计列表、时区与 Console SSE 生命周期 | 复用完整入口回归。Ingest 浏览器流补只读账号的可见与拒绝边界。 |
| Web → Ingest → Kafka | 浏览器建映射和 HTTP 接入点、真实设备推送、读取 Kafka 并检查 OCSF | 扩充已有主流程验证令牌轮换与新旧令牌效果。Syslog 帧与 Kafka 位移分别留在通道测试。 |
| Ingest 样本试算 | 编译失败与逐条命中统计 | 在原用例增加可观察的预览内容，再补向导阻止使用过期试算的交互。 |
| Kafka 发布和消费 | 分区键选择单测、两项需显式 broker 的消费集成用例 | 检测到 CI 集成入口没有 provision broker；补真实分区验收，验证两项既有用例确实运行。 |
| 审计 | IAM 自有变更的审计事务、Ingest 鉴权守卫与设备推送不审计 | 增加跨服务写入失败恢复与审计事实去重。 |

## 验收记录

- Kafka 真 broker 集成覆盖最早位移、失败后重投和同实体在生产批次内的分区顺序。PostgreSQL 集成覆盖 FortiGate 内置规则、管理变更与审计共同提交、失败重投及去重。测试入口为各用例创建临时库。
- Chromium 12 项端到端用例通过，包含 Web 选择映射并通过真 HTTP 推送、Kafka 读回、IAM 审计事实、旧令牌拒绝、Kafka 表单焦点和只读权限边界。Console SSE 通过真实副本校验优雅关闭。桌面和 390 × 844 窄屏核验双语、浅色与深色、FortiGate 只读与复制、Kafka 字段错误及 Syslog 创建和危险操作确认。
- 本地重启暴露 Ingest 存量表存在而迁移账本缺失。迁移入口使用 `ingest.goose_db_version`，校验并登记已有首版表后再迁移。真实 PostgreSQL 回归验证了空库、旧表保留记录和重复执行。
- 容量抽测使用 8 逻辑核、16 GiB 的本机，隔离单节点 Kafka 与 Redis，HTTP 每批 1000 条短 JSON，实际跑了 30.03 秒。计划输入 1,500,000 条，受理 1,488,508 条，Kafka 确认同样数量，无已受理后丢弃、解析失败或发布重试。吞吐约 49,567 条/秒，从 HTTP 接收到 Kafka 确认的 P99 为 447 ms，队列峰值 10,000，GC 2169 次、暂停合计 442 ms。存在受理前拒收，持续 5 万 EPS 容量验收仍开放。
