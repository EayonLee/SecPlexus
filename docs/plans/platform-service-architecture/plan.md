## 1. 验证一条完整业务链

- [x] 用现有“自定义角色分配”流程验证 router → handler → service → repository → PostgreSQL → Result → Web，保留组织范围、委派限制、版本检查和审计事务。变更契约先用针对性测试确认预期失败。
- [x] 在同一试点验证 chi 分组/路径参数及 GORM 的事务绑定、现有锁、更新计数和错误映射；明确 GORM、pgx/SCS、Goose 的连接池和关闭归属。局部具体类型够用时不加接口。
- [x] 验证 Result 的公共 schema、错误码注册表、现有 Go/TypeScript 生成链及一次真实前端解析；不在 helper 与 DTO 各定义一套 wire contract。
- [x] 用真实 PostgreSQL 验证角色变更与审计一起提交或回滚，并验证 Session 保存失败时的响应/Cookie 及已提交状态。复用现有失败验证，不为试点建设通用故障注入框架。

**完成条件**：正常与核心拒绝/失败路径保持正确；组件确实减少重复代码。若失败，先记录具体障碍并调整最小接入方式；不能削弱授权/锁，也不能悄悄换框架或扩展需求。试点不部署额外临时接口。

## 2. 一次性切换 HTTP 契约及调用方

- [x] 在 `src/contracts/common/` 定义 Result schema 和错误码注册表，复用现有生成入口产出 Go/TypeScript 类型与常量；通用码、模块码、HTTP 状态及安全消息保持一致。
- [x] 由 `httpx` 承担请求绑定，`result` 承担 Success/Created/NoContent/Fail 输出，模块边界负责业务错误映射。厘清契约验证与 Decode 的职责，同一结构规则只验证一次；应用层保留权限、业务状态和事务检查。
- [x] 整理公开、内部和 SSE 入口的真实中间件顺序，保护 Session 提交、Origin/CSRF、异常恢复和响应提交；保留 204/流式例外，不新增 CORS 功能或万能响应缓冲器。
- [x] 同批更新 IAM/Console、Web 客户端、iamclient、脚本和受影响测试，避免先换服务端再留调用方到最后。用实际路由遍历与 OpenAPI 对比替代源码正则作为唯一检查。

**完成条件**：全部现有消费者可运行，普通 API 统一 Result；404/405、绑定失败和错误状态映射有边界测试，204/SSE 不被包装。没有并行旧信封或重复解码规则。

## 3. 按用例整理业务、仓储和迁移

- [x] 将 handler 直接查库的逻辑移到对应仓储；用例集中授权、组织范围、事务与审计。简单调用直接表达，不为 Console 透传或每张表添加 service/interface。
- [x] 普通 CRUD 迁入试点确认的 GORM 实现；锁与 PostgreSQL 特有操作保留必要参数化 SQL 并注明理由。所有同一事务的操作使用同一个事务执行器，不从仓储方法回到根连接。
- [x] 对照 Spec 业务矩阵保持现有行为，复用授权/会话/并发集成用例；只为本次变更的事务或状态规则补缺口。确认不再调用后删除 sqlc 查询、生成物与生成步骤，不删除仍被 SCS 使用的依赖。
- [x] 将现有 migrations 和 embed 移到模块目录，同步构建/命令，保持历史脚本、编号、版本表和迁移锁。验证空库、带数据升级及必要恢复路径；仅新增迁移需要时才补非事务 DDL 等专门测试。

**完成条件**：handler 不再直接查库，事务边界可追踪，原有数据和权限规则保持；迁移仍使用 Goose，不以 AutoMigrate 或默认清库代替升级。
