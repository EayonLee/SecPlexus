# 平台架构审查与整改顺序

当前已完成源码入口、迁移、现有规范与目标设计的首轮静态对照。每一阶段在此登记“发现、影响、归属、修改及验证结果”，能由既有专题承接的任务链接回原计划。上线结论以对应服务、数据库或浏览器的实测为准。

仓库入口、模块边界、事件交付、Web 维护和验证链路的逐项审查见[仓库审查表](review.md)。

## Go 模块结构对齐

| 模块 | 源码确认的差异 | 本轮调整与验收 |
|---|---|---|
| IAM | 同一 Gin 引擎已区分用户与服务凭证中间件；业务前缀曾在各条路由重复。 | `routes.go` 创建业务组，组内路由按账户、用户和角色文件维护。保留会话提交、来源限流、代理信任及服务授权链顺序。 |
| Console | 已使用 Gin 分组与 SSE；上下文响应 DTO 和就绪响应散在 handler 与 router。 | DTO 归 `internal/model`，就绪响应归 handler。保留流式刷新、取消及运行中重新鉴权。 |
| Ingest | 管理和设备推送各建一套 Gin，引擎外再用标准库 mux 分流。Kafka 包只提供客户端安全选项转换，Event 仓储包名重复强调存储。 | 单个 Gin 引擎，`routes.go` 创建各业务组，`inputs.go` 和 `mappings.go` 登记组内路由。`connection/kafka` 维护连接选项，`repository/event` 维护事件。复用已有大包推送、设备令牌、管理审计与事件写入回归。 |

跨服务核对同源认证、请求限制、错误响应和 SSE。Ingest 入站与出站 Kafka 的连接配置整改见本页九项实施。升级已有 SASL/TLS 部署时需显式配置入站身份。Console 权限目录自检与 IAM 服务白名单也需一起审查，避免无效的启动检查。新增应用的根命令注册按阶段 2 实施。

三套 Go 服务的竞态测试通过，受影响包通过 Go lint。导入限制已用临时模块验证，顶层及子目录的路由文件直接导入数据库驱动均被拒绝。使用配置中的 PostgreSQL、Redis 和 Kafka 运行 IAM 与 Ingest 浏览器套件，13 个用例通过；同一次运行验证了 Console SSE 在副本停止时关闭。[IAM 浏览器用例](../../../src/apps/web/tests/e2e/auth.spec.ts) · [Ingest 浏览器用例](../../../src/apps/web/tests/e2e/ingest.spec.ts)

## 实施与复审

| 阶段 | 交付与验证 |
|---|---|
| 1. 复核存量 | 维护每个真实模块的用例与依赖清单。复用现有集成和 E2E，核对 README、启动脚本、模块实际行为、既有计划中标为已完成的事项。每项记录证据与尚未跑到的路径；出现偏差，先补可复现用例，再更新实现及对应设计。 |
| 2. 统一应用入口 | 应用上述目录与用法约定。检查同源 API 权限、配置作用域和错误模型；保留 Web 原生框架、IAM 特有命令，以及 Console 的 SSE 取消机制。用一个现存模块演练独立与整栈启动，逐模块验证特殊能力。 |
| 3. 贯通一个事件类别 | 先修正常启动分流，再实施字段目录、规则校验、带本地化元数据的字段 API 与浏览器编辑。验证两个来源归一到同一字段，未通过契约的消息进入诊断流。以规则新建、预览、保存、复开和权限拒绝作为跨层验收。 |
| 4. 验证 CK 的数据与部署 | 先定投影及数据库权限，再走空库初始化、升级、手改库检测、批次重放和保留期。按照[存储验收](../event-contract/storage.md)记录常用查询扫描量、写入速率和积压恢复时间。在工作负载及保留期确定后，用日事件量、实测压缩后每条字节、保留天数和副本数估算容量，另计合并、回填和备份空间。 |
| 5. 演练故障与恢复 | 对接收与归档分别观察有效/失败记录、分区积压和最旧未归档时间。模拟 CK 不可用、恢复及重放，确认归档故障的隔离范围；识别 Kafka 已过保留期的缺口。用隔离环境从备份恢复 CK 表和版本信息，核对代表性 Event、证据引用和续读位移。记录实测可恢复范围与耗时，作为确定 RPO/RTO 的依据。 |
| 6. 验证部署与交接 | 将开发源码、当前 Compose、目标部署清单分列。归档启用前确认 CK 版本、连接与 TLS、迁移身份、读写权限、配置校验、就绪状态、退出排空及升级顺序。使用明确的测试连接或显式隔离容器。部署/升级前后运行只读漂移检查，输出已应用版本、实际差异与处置路径。 |
| 命名复审（随各阶段） | 对已有模块、配置、文件及代码标识符选取端到端用例，逐项比对输入、规则、处理中间值、发布实体与数据库字段的名称和含义。优先登记会影响分类、检测或跨模块理解的差异。每项记录采用的标准条目、行业用例或平台约定，以及涉及的消费者；公开标识符的改名另评兼容影响。验收依据见[安全领域术语](../../development/backend-structure.md#安全领域术语与来源)。 |
| 7. 后续变更准入 | 新增 app 时复核模块职责和根入口；改事件字段时复核契约、兼容性、列投影、下游规则、标签和模型资料；改数据库时复核生成物、迁移、真实结构及恢复。用合并检查覆盖可机械判断的规则，业务方向、字段意义、保留策略与数据访问范围由相应模块维护者评审。 |

每次整改都随改动更新业务、技术、数据或部署架构的对应章节及模块 README。关闭事项时附现有或新增用例、执行结果、仍受限的环境和回退方式；历史结论与新的验收结果分开记录。Alert 的实际业务状态机与迁移在 correlator 落地时单独评审。

## 开发到运行的交付与交接

本节把公开实践转成各模块的实施与验收项。当前产品范围为 IAM、Console、Ingest、Web 和通过独立进程运行的 Event 归档。correlator 与 Alert 保留独立消费、按稳定引用回查 Event 的设计边界，未来立项时再确定其实体、接口、测试与部署。

| 阶段 | 本项目的做法 | 交付证据与负责模块 |
|---|---|---|
| 开发与迭代 | 从一个真实用例和脱敏样本出发，在字段拥有者处定义含义、类型、范围和单位；先固定失败用例。区分翻译修订、新增可选字段及改变旧值含义。协议变更在同次评审列出受影响的规则、消费者、列映射和回退条件。 | Ingest 的字段差异、预览与真实发布一致的样本；Web 用同一目录版本复开规则；IAM 核对权限派生物和真实拒绝路径。依据是从权威字段定义生成各消费产物的公开做法。[Elastic ECS](https://github.com/elastic/ecs/blob/main/USAGE.md) |
| 升级 | 对会影响已部署读写方的变更分阶段执行：先扩展结构并准备能识别旧、新版本的读方，再切生产者与 Web，观察完成后另行收缩旧结构。已应用迁移保持可追溯。对已明确允许清理的早期数据记录删除范围、备份与不可逆影响，不把日常版本升级建立在清库上。 | Ingest 在隔离环境验证空库、上一受支持版本以及切换时积压的消息。记录配置、制品、契约、目录修订、PG/CK 迁移版本和 Kafka 各分区切换位移。GitLab 将应用仍可能引用旧列作为拆分迁移的依据。[GitLab 迁移实践](https://docs.gitlab.com/development/database/avoiding_downtime_in_migrations/) |
| 部署与停止放量 | 先离线检查配置及依赖版本、迁移身份、实际结构和可用空间，再部署兼容读方与写方。在隔离环境用一小组代表性接入样本比对新旧版；有分批发布能力时，在发布环境复用同一批信号。当前源码可运行四个应用，Compose 所含服务以实际清单为准。 | 每个版本分别记录受理、解析失败、发布重试、消费积压及回读值。出现非法记录进标准流、字段语义改变或已提交位移对应记录无法解释时停止放量，保留位移和兼容读方。异常率和时延阈值按实测基线约定。回退生产者前验证保留表结构仍支持它。[Google SRE 发布验证](https://sre.google/workbook/canarying-releases/) · [当前部署清单](../../../deploy/compose/compose.yaml) |
| 维护与恢复 | Ingest 跟踪入站、发布、最旧未归档时间、可用 Kafka 保留窗口、CK 容量与保留策略。备份同时记录表结构、迁移版本、数据截止点和按分区可重放的起点；IAM 恢复按其 README 在开放流量前处理会话。 | 将 CK 备份恢复到隔离目标，在同一份数据上检查表结构、样本和逻辑计数。以备份确定覆盖的连续位移为依据选取恢复起点；位移不确定时优先在隔离组验证可覆盖的较早起点，并区分重复、缺口和已过期记录。由演练结果给出 RPO、RTO 和下一次复验条件。[ClickHouse 备份恢复](https://clickhouse.com/docs/concepts/features/backup-restore/overview) · [Kafka 消费组运维](https://kafka.apache.org/41/operations/basic-kafka-operations/) |
| 故障定位与关闭 | 从用户可观察的故障出发，按 Web 请求、IAM 授权、Ingest 解析、Kafka 发布、CK 归档的实际路径缩小范围。同步操作跟踪 request_id，异步事件增加 event_id、topic、分区和位移。每次提出可验证的原因，并记录能排除它的检查。 | 以 403、预览与真实输入差异、发布重试、归档漂移分别做有界演练。记录影响、首个异常环节、恢复证据、后续回归及所属 README 的修订位置。只在隔离目标注入 DDL 或依赖故障。[Google SRE 排障方法](https://sre.google/sre-book/effective-troubleshooting/) · [项目日志约定](../../development/observability.md) |

## 九项整改实施顺序

| 交付 | 验收 |
| --- | --- |
| 入站/出站 Kafka 连接、按记录确认、Kafka 重读标识、HTTP 确认 | 两侧配置独立解析，有效和无效证书与协议走同一配置入口；部分成功只重试失败项；提交失败及重读保持标识；停止或发布超时时 HTTP 只反馈已确认的前缀。参考 [Kafka 交付语义](https://kafka.apache.org/41/design/design/) 和 [OpenTelemetry Collector 的可靠性](https://opentelemetry.io/docs/collector/resiliency/)。 |
| 规则来源、数据库修订、失败数据处置 | 在同一事务维护规则及修订，用实际生效快照校验来源字段；诊断消息中确认没有原文并能按坐标定位存储失败。参考 [Logstash 失败队列治理](https://www.elastic.co/docs/reference/logstash/dead-letter-queues)。 |
| 管理 API 与 Web | 有上限的服务端分页，详情和规则定义单独查询；集成检查授权、分页、筛选和老调用入口，浏览器验证查找、刷新、绑定和编辑。参考 [Kubernetes 集合分页](https://kubernetes.io/docs/reference/using-api/api-concepts/#retrieving-large-results-sets-in-chunks)。 |
| ClickHouse 验收和运行文档 | CI 独占依赖继承已授权的容器测试入口，缺测试地址时强制任务失败；空库及既有表演练分别核对迁移、数据校验和恢复。根与模块 README 对齐可运行入口、流程、命名和故障处置。参考 [ClickHouse Backup and Restore](https://clickhouse.com/docs/operations/backup)。 |

接入热路径沿用现有队列和 Kafka 消费组，按确认结果缩小每次重试的批次。HTTP 等待期间不持有数据库连接和锁。规则历史按变更数增长，写入与当前配置在同一事务，读取按规则 ID 和版本定位。管理列表只读取当前页，过滤成本和排序索引以实际扫描计划核对。现存表采用前向迁移保留数据。容量测试和生产保留期的具体取值以目标环境确认。

### 执行结果

| 审查项 | 已交付与验证 |
| --- | --- |
| Kafka 连接配置 | 入站和内部总线凭据分别加载，非法协议及缺失凭据在配置加载时拒绝。单测核对两个方向的凭据和配置快照。 |
| Kafka 重放与 Event 身份 | 真实 broker 返回混合结果时只保留未确认项。验证提交失败后重读保持 ID，以及相同正文的不同位移有独立 ID。 |
| HTTP 回执与停机 | 回执按 broker 确认的连续前缀计数。已验证零确认的 503、部分确认和真实设备推送。结果未知时可重试，同一设备再次提交仍可能产生重复。 |
| 失败数据治理 | 解析诊断收敛为原因、来源和修订，存储失败通过 Kafka 坐标回查；CI 用例校验失败记录不含原报文。部署运营方配置失败主题权限和保留期。 |
