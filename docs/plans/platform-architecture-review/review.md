# SecPlexus 仓库审查

下表记录初始审查。九项整改及验收见[实施记录](plan.md#九项整改实施顺序)。

审查覆盖根文档与开发命令、IAM、Console、Ingest、Web、共享 Go 包、部署和持续集成。以当前工作树中的实际入口为准。优先级按数据安全、交付可靠性和维护成本排列。运行数据量、故障发生频率与部署覆盖以对应环境的实测为准。

| 优先级 | 范围 | 发现与影响 | 整改目标与验收证据 |
| --- | --- | --- | --- |
| 高 | Kafka 连接与配置 | Ingest 的外部 Kafka 接入和内部事件发布共用出站安全设置，对不同信任域使用独立凭据的能力缺失。客户端在装配连接时读取口令，用无效的 Kafka 安全协议运行离线检查依然通过，运行期则会拒绝。[依赖装配](../../../src/apps/ingest/internal/bootstrap/serve.go) · [Kafka 安全选项](../../../src/apps/ingest/internal/connection/kafka/security.go) | 分开管理外部输入与内部总线的连接安全，在配置阶段验证显式选择的协议和凭据引用。以不同连接身份和配置失败用例核实隔离，记录部署切换步骤。[OpenTelemetry 输入与输出配置](https://opentelemetry.io/docs/collector/configuration/) |
| 高 | Kafka 重放与 Event 身份 | 生产端只返回批次首个错误，上层因此可能重发已经确认的记录。外部 Kafka 重读会重新解析，现有 Event ID 含进程和序号，跨进程重读同一源记录可能获得新 ID，ClickHouse 对已发布 Event 的去重覆盖不了这类重投。[Kafka 发布](../../../src/apps/ingest/internal/publish/kafka.go) · [外部消费](../../../src/apps/ingest/internal/channel/kafkachannel/consumer.go) · [事件组装](../../../src/apps/ingest/internal/pipeline/pipeline.go) | 明确各通道回执边界。处理部分确认，并按来源记录的稳定身份定义 Kafka 重读策略。验证部分成功、提交失败、重启、逻辑计数，以及内容相同的两次独立观测仍可区分。[Kafka 交付语义](https://kafka.apache.org/41/design/design/) |
| 高 | HTTP 受理与停机 | HTTP 的 `202` 表示进程内受理。队列尚未获得 Kafka 确认时，异常退出或超时排空可能失去已受理记录。对要求可靠交付的来源，接入说明和调用方需要明确理解这层回执。[设备响应](../../../src/apps/ingest/internal/channel/httpchannel/handler.go) · [发布排空](../../../src/apps/ingest/internal/pipeline/pipeline.go) | 明确协议交付承诺。对需要持久确认的通道评估回执与缓冲方案，用停进程、broker 延迟及部分受理用例对账。当前 README 已写明进程内受理边界。 |
| 高 | 诊断数据治理 | 失败消息可保留设备原始报文。解析失败主题和存储隔离主题应按原始遥测的敏感级别管理。仅约束应用日志无法覆盖这两条路径。[诊断事件正文](../../../src/apps/ingest/internal/pipeline/pipeline.go) · [存储隔离](../../../src/apps/ingest/internal/consumer/worker.go) | 定义诊断主题的访问、保留、脱敏、大小与重放规则。以含脱敏标记的样本验证正常与异常路径，并记录原文需要受控保留的条件。 |
| 高 | 规则修订追溯 | PostgreSQL 规则有修订号，首版迁移也描述了 `metadata.spx.mapping_version`，但运行时加载查询和发布正文没有携带规则 ID 或修订。更换或修改规则后，单靠接入点 ID 和平台契约版本无法定位旧事件用了哪版规则。[规则列注释](../../../src/apps/ingest/migrations/postgresql/00001_init.sql) · [加载查询](../../../src/apps/ingest/internal/repository/queries/inputs.sql) · [事件正文](../../../src/apps/ingest/internal/pipeline/pipeline.go) | 将实际用到的规则身份与修订一并装入不可变快照，随 Event 或诊断记录发布，并保留可追溯的规则版本。用同一接入点切换规则的回归对照前后消息。 |
| 中 | 新维护者的入口 | 根中英文 README 在快速开始遗漏 Ingest 的服务凭证，启动注释和构建命令描述仍使用旧模块数量；Compose 没有 Ingest、Kafka 或 ClickHouse。读者需在多个章节判断哪些服务已能运行。[中文入口](../../../README.zh-CN.md) · [英文入口](../../../README.md) · [Compose](../../../deploy/compose/compose.yaml) · [构建脚本](../../../scripts/build.mjs) | 两种语言各提供同一份可运行模块清单、完整启动条件、首条事件验收以及 Compose 覆盖范围。用空工作区按 README 验证配置生成、启动和第一条数据链路。 |
| 中 | 文档中的产品边界 | 模块 README、目标架构和实施计划各自维护能力描述。部署文档已列出可选 Event 持久化，技术概览仍把消费组置于下游规划，数据访问指南仍把它列为下一阶段。[部署现状](../../design/architecture/03-deployment-architecture.md) · [技术概览](../../design/architecture/02-technical-architecture.md) · [数据访问](../../development/data-access.md) | 根入口指向可运行模块，模块 README 说明现有契约及前置条件，架构图显式标出规划和独立部署。以普通读者能准确区分 Event 与 Alert、Kafka 与在线事件存储为验收。 |
| 中 | Web 列表与接口规模 | Ingest 的两个管理 API 全量查接入点与规则，规则列表含完整定义。Web 在浏览器过滤分页，详情定时轮询整张接入点表。规则一多，数据库、网络和客户端负担会同时增加。[接入点查询](../../../src/apps/ingest/internal/repository/queries/inputs.sql) · [规则查询](../../../src/apps/ingest/internal/repository/queries/mappings.sql) · [详情查询](../../../src/apps/web/src/spx/pages/ingest.tsx) | 明确服务端列表摘要、稳定排序与分页契约。详情按 ID 获取并复用同一查询。用代表性记录规模核对响应字节、扫描量和分页稳定性。 |
| 中 | 规则编辑与并发 | 规则更新按 ID 修改并递增版本。两个操作者基于同一版编辑，后一次更新可覆盖前一次，页面拿到的现有版本尚未参与写入前置检查。[规则更新 SQL](../../../src/apps/ingest/internal/repository/queries/mappings.sql) · [规则编辑](../../../src/apps/web/src/spx/pages/mappings.tsx) | 以已有版本做更新前置条件。版本不一致时提供可恢复冲突，保留草稿。用两个会话验证。 |
| 中 | Web 结构 | 接入页约 1,300 行，串起向导、列表、详情编辑、令牌和批量操作。规则页约 1,180 行，同时管理样本、解析定义、字段目录和列表。路由虽已独立，修改一个流程仍需在同一文件跨多段状态查找。[接入页](../../../src/apps/web/src/spx/pages/ingest.tsx) · [规则页](../../../src/apps/web/src/spx/pages/mappings.tsx) | 按接入列表、详情、创建流程和规则编辑工作区拆分。已有表格、弹窗和目录 API 延续统一入口。以浏览器旅程固定打开、保存、验证、异常与键盘操作。 |
| 中 | Event 目录版本 | `catalog_revision` 对本地清单取哈希，运行目录还读取多个上游文件。快照内容在清单未变时发生漂移，修订可能无法反映运行字段差异。跨版本字段及枚举差异也缺少独立检查。[目录加载](../../../src/apps/ingest/schema/events/catalog.go) · [契约计划](../event-contract/plan.md) | 使修订反映实际解析后的目录或完整锁定输入，用前一发布版本校验路径、必填、枚举、单位和双语修订。用英文定义或枚举变化验证缓存更新。 |
| 中 | ClickHouse 验收与升级 | 默认集成 CI 未提供 ClickHouse 测试端点，归档测试在缺少地址时跳过。首版 DDL 与漂移核对已经具备，跨版本账本和恢复证据仍开放。[CI 集成配置](../../../.github/workflows/ci.yml) · [集成测试前置条件](../../../src/apps/ingest/internal/consumer/worker_integration_test.go) · [存储计划](../event-contract/storage.md) | 将归档真实组件验收接入明确的 CI 任务或发布闸门，把预期执行时的跳过视为缺少证据。增加已应用迁移校验、前版升级和备份恢复演练。[Snuba 消费与 ClickHouse 写入](https://getsentry.github.io/snuba/architecture/consumer.html) |
| 中 | Console 与 IAM | Console 启动时调用 IAM 权限目录自检，现有 Console 服务白名单没有对应目录读取权限。当前就绪路由只报告 HTTP 进程层的可用性，启动就绪和授权通路正常是两个可观察状态。[Console 装配](../../../src/apps/console/internal/bootstrap/serve.go) · [IAM 服务权限](../../../src/apps/iam/config.yaml) · [Console 就绪处理](../../../src/apps/console/internal/handler/server.go) | 让自检调用与 IAM 的授权模型对齐，独立解释 HTTP 就绪和依赖降级。用真实服务凭证测试授权目录检查与拒绝路径。 |

先处理数据交付、凭据和规则追溯，再做文档与部署入口、列表和 Web 维护边界。文件的组织以职责和变更原因划分，可参考 Grafana 对业务包与公共设施的分界。数据管道则用明确的输入、处理、输出和消费者角色，参考 OpenTelemetry 与 Snuba 的文档入口。[Grafana 包层级](https://github.com/grafana/grafana/blob/main/contribute/backend/package-hierarchy.md) · [OpenTelemetry Collector 配置](https://opentelemetry.io/docs/collector/configuration/) · [Snuba Consumers](https://getsentry.github.io/snuba/architecture/consumer.html)

本轮通过三套 Go 服务及共享 Go 包的竞态测试、Web 类型检查和 77 个 Web 单测。四应用离线配置检查和内置 FortiGate 规则的 PostgreSQL 集成测试通过。显式移除 ClickHouse 测试地址时，归档集成用例确实跳过。上述生产语义及容量风险主要依据源码和已有计划，未在共享运行环境复现。
