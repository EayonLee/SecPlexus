# 审计与角色管理简化、设置区合并 — 需求与方案

## 1. 背景

IAM 管理区存在四处被用户明确指出的过度设计：

1. 审计日志分成两个入口、两个页面、两个标签，查同一张 `iam.audit_events` 表，只是过滤条件不同。
2. 角色与权限页顶部有列不下的角色标签；创建角色走模态框，需要手填「角色标识」；列表展示「类型」；查看与编辑分离成两个入口。
3. 角色的 `code`（角色标识）与 `kind`（类型）对使用者没有实际价值，却牵连数据库约束与内置角色的识别方式。
4. 顶栏头像菜单里「个人中心」与「系统管理」是两个并列入口，左侧菜单再拆「个人资料 / 账号安全」两项，属于同一件事的重复入口。

本需求的目标是**减少概念数量**：删掉分支、删掉标签、删掉用户无法理解的字段，把同一件事收敛成一套实现。不做任何历史兼容。

## 2. 决策

### 2.1 审计：单一列表

- 删除两个审计导航项，合并为一个「审计日志」。
- 删除顶部标签，替换为搜索条件：**操作者、时间范围、结果**。
- 后端合并为单一端点 `GET /api/v1/iam/audit-events`，授权在服务端判定：具备 `iam.audit.read` 即查看全部审计。
- 审计事件没有范围维度，不存在按范围列裁剪可见范围的过滤，也没有第二套范围权限。

**理由**：审计的事件模型（`action`、`actor`、`outcome`、`target_type`/`target_id`）本就统一；分页只是过滤条件不同，拆成两个入口没有边界收益。参考 GitLab（`/audit_events` 单一流 + scope 过滤）、Keycloak（Events 单页 + 筛选器）的做法。

### 2.2 角色：删除 code 与 kind

- 数据库没有 `iam.roles.code`、`iam.roles.kind` 两列，也没有依赖它们的 CHECK 约束与唯一键。
- 角色只用 `id`（UUID）关联；名称、说明、权限即全部可编辑属性。
- 内置角色只有一个：**超级管理员**。它由启动配置写入数据库，`roles.builtin=true`，持有权限目录全部有效键；页面只读，不可改名、改说明、改权限、删除。
- 不再有按业务代码识别内置角色的分支，也不再铸造内置业务角色；内置身份只由 `roles.builtin` 表达。
- 保留「平台必须至少一个有效超级管理员」（`ProtectPlatformAdministrator`）：持有内置超级管理员角色的账号不可停用、不可删除，这是平台级安全底线。

### 2.3 角色列表与抽屉

- 删除顶部角色标签区。
- 搜索条件（名称）+ 功能按钮（创建角色）**同一行**：搜索靠左，按钮靠右。
- 列表列：名称、说明、用户数、操作。删除「角色标识」「类型」两列。
- 内置行带「内置」徽标，操作列只保留权限查看，没有编辑与删除入口。
- 「查看」改为「编辑」，与创建共用右侧抽屉（`SheetPanel`）。
- 创建抽屉：角色名称、角色说明、角色权限（创建时即选择权限）。
- 编辑抽屉两段式：**角色信息**（可改）、**角色权限**（可改）。用户归属用户管理，抽屉不重复展示角色用户。
- 删除角色前必须判断该角色是否有用户持有；有则禁止删除并给出明确原因（409）。内置角色一律拒绝删除。

### 2.4 Settings 合并

- 头像菜单「个人中心」「系统管理」合并为一项：英文 `Settings`，中文「设置」。
- 左侧菜单合并「个人资料 / 账号安全」为**一项**并置于首位，其后是角色与权限、用户、审计。
- 路由收敛：`/settings/profile` 与 `/settings/account` 合并为单一 `/settings`。
- 管理区路由由 `/management/**` 迁入 `/settings/**` 之下：`/settings/roles`、`/settings/users`、`/settings/audit`。

## 3. 行为契约

| 项 | 契约 |
|---|---|
| 审计列表 | `GET /api/v1/iam/audit-events?actor=&from=&to=&outcome=&limit=&offset=`；具备 `iam.audit.read` 即返回全部事件，无范围过滤 |
| 审计权限 | `iam.audit.read` → 全部审计；不存在按范围裁剪的第二权限 |
| 角色创建 | `POST /api/v1/iam/roles`，body 仅 `name`、`description`、`permissions`；`id` 由服务端生成 |
| 角色更新 | `PATCH /api/v1/iam/roles/:id`，body `name`、`description`、`version` |
| 角色权限 | `PUT /api/v1/iam/roles/:id/permissions`，body `permissions`、`version` |
| 角色删除 | `DELETE /api/v1/iam/roles/:id?version=`；`user_count > 0` 返回 409 并说明原因；`builtin` 角色一律拒绝 |
| 内置保护 | 内置超级管理员角色不可改名、改说明、改权限、删除；配置管理员账号不可删除、停用、在页面改密 |
| 路由 | 设置区统一在 `/settings` 之下，无 `/management` 前缀 |
| i18n | `en` / `zh-CN` 目录键完全对齐，无孤立键 |

## 4. 验收

1. 审计页只有一个入口、一个列表，顶部是操作者/时间范围/结果三个筛选条件，无审计分类标签。
2. 角色页顶部无角色标签；搜索与「创建角色」按钮同一行，左对齐/右对齐。
3. 角色列表展示名称、说明、用户数；无「角色标识」「类型」列。
4. 创建角色为右侧抽屉，含名称、说明、权限三项，创建即选权限。
5. 编辑角色抽屉两段式：信息可改、权限可改；内置行只读。
6. 删除有用户持有的角色被拒绝并显示原因；内置角色没有删除入口，服务端同样拒绝。
7. 头像菜单只有一项 `Settings`；左侧菜单第一项为设置，其后为角色、用户、审计。
8. `/settings` 单一路由；旧 `/settings/profile`、`/settings/account`、`/management/**` 不再存在。
9. 数据库无 `iam.roles.code`、`iam.roles.kind` 列；`roles.builtin` 标记内置超级管理员。
10. 文档、README、索引、i18n、路由常量全部同步，无残留引用。

## 5. 不做

- 不保留任何旧路由重定向、旧字段兼容、双写或过渡层。
- 不新增按范围强制管理员的机制：管理员能力由角色与权限表达，超级管理员始终兜底。
- 不改动审计事件本身的字段语义；审计仍记录 `target_type`/`target_id`。
