## 1. 实施原则与依赖顺序

这是一次完整交付，下面是任务依赖，不是分批发布承诺。允许实施中的短暂未完成状态，交付结果不得同时保留 Chi/Gin、Authboss/Gin 两套认证编排、两套配置解析或两份契约真源。

```text
T1 基线 → T2/D3 HTTP/认证组合 → T3 HTTP 基础 → T4 IAM/Console 迁移
       → T2/D2 配置能力 → T5 配置替换
       → T2/D1 契约工具 → T4 中的契约真源切换
T4 + T5 → T6 数据与真实业务范例 → T7 全链路验收与收敛
```

D3 决定 HTTP/认证组合，D2 决定配置替换，D1 决定契约真源切换；各自未通过时只阻止其依赖任务，不让尚未选定的接口生成器阻塞 Gin 基础重构。D1 未决时现有契约仍是唯一真源，可以维护 Gin 路由与调用方；不得切换真源或宣布 R4/A6 完成。整个交付仍须完成所有门槛，失败时按既定规则修订方案。文档随任务更新，T7 负责最终一致性检查。

本次文档批准后按任务推进，不为已批准范围逐项重复询问。若工具无法满足约束、需要改变接口业务语义或扩大范围，先提供证据、修订方案后审核；不通过偷偷加兼容层继续施工。提交、推送、部署和代理委派不包含在实施授权中。

### T2：完成三项能力验证并固定方案

| 必验情况 | 验证证据 |
| --- | --- |
| required、optional、nullable、PATCH 缺省/null/零/false | Go 绑定、生成 OpenAPI 和 TS 使用方式一致，不手补生成结果 |
| `$ref`/组合类型、枚举、Result 泛型或等效响应类型 | required data/code/message/request_id 等约束未丢失；错误响应可消费 |

| Cookie、CSRF、内部凭证和公开/内部操作 | 文档安全方案/头部及实际保护一致，不把 security 元数据当认证实现 |
| 201、204、404、405、413、415、401/403/503 | 正文、媒体类型、状态、必要头部和错误码正确 |
| SSE、取消及响应开始后的失败 | 文档描述流；生成消费方式不强制 JSON；执行链不缓冲/二次响应 |
| action 元数据、operationId、路由参数 | 可与现有权限目录及 Gin 实际路由检查联动 |
| 生成稳定性与唯一性 | 同一输入连续生成无差异；Go/TS 编译通过；明确消除哪些旧定义 |
