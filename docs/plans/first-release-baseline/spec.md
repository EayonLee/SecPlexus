# SecPlexus 首次发行基线

日期：2026-11-28。状态：已实施主要链路，验收进度见 [实施计划](plan.md#本轮验证结果)。范围：Ingest、IAM、Console、Web、共享依赖、工程规范及本地 Compose 验收。

## 交付边界

首次发行从空环境安装。本轮一次性统一配置、接口、代码和表结构。删除只服务于试制版本的配置键、命令、路由、字段、读取分支、种子数据、迁移及其专用夹具。开发环境按新基线重新创建资源。开发旧制品和旧数据按可丢弃处理，兼容工作从首次正式发行后的下一版开始立项。

- 每个存储所有者按数据库保留一份首版建库基线。Ingest 的 PostgreSQL 与 ClickHouse 分开，IAM 保留自己的 PostgreSQL 基线。现有开发库和 Kafka 位移无需迁入。保留当前结构校验、幂等初始化和基线同版本恢复。
- 只保留当前形状的 HTTP `/api/v1` 和 Event 契约 `v1`。移除旧名别名、双读双写、旧路由跳转和按版本猜测字段的分支。源代码、生成物、模板、文档同时切换。
- 规则修订、事件身份、Kafka 位移、权限校验、接收保护和审计历史是首版的运行契约。规则回退使用当前平台生成的修订。同版本恢复使用同一基线生成的备份。
- 重建仅操作明确属于本次隔离验收的容器、卷、数据库、主题、消费组和 Redis 键。开发者需要重建自己的环境时，操作手册列出具体资源与删除后果。Compose 启动发现旧基线时提示重建，预检保持只读。

本规格确定 Web、IAM、Ingest 和当前 Console 的收尾范围。旧计划的验收记录可用于核对回归。发生冲突时以本规格为准，包括原先的试制兼容、可选 ClickHouse、Event 过期以及安装包。已实现的页面交互沿用各自专项规格。[架构复审](../platform-architecture-review/plan.md) · [商业交付](../commercial-delivery/plan.md) · [Event 契约](../event-contract/spec.md)

## 默认部署配置

- 根模板按 Web、应用及依赖分组，集中提供常用安全策略、资源限制、日志及连接设置。Web 访问来源随本机端口派生，分开部署时再填写地址覆盖。自带依赖由 Compose 寻址，外接 PostgreSQL 与 Redis 各用一个 URL。低频调优在根模板的所属模块中以注释展示，模块 YAML 定义运行默认值。嵌套凭据和内部参数由模块持有，测试连接见测试指南。
- 公共和私有环境文件沿用相同分组及注释。已公开的环境变量注明作用范围、单位及空值语义。整栈 Compose 注入 Ingest 的限流、解析队列、批量发布和接入刷新配置。独立运行使用外接依赖地址、原生 TLS 和文件日志选项。
- IAM、Ingest 各构建一个镜像供同模块的任务和进程使用。IAM 的迁移同步权限目录，初始化只负责首次创建管理员，显式管理员维护使用已同步的角色。
- Ingest 保存与恢复规则复用同一套归一化和编译，保存时直接用编译结果验证样本。仓储按预期版本写入规则和修订。 [Compose 构建](https://docs.docker.com/reference/cli/docker/compose/build/#description)

## 共享依赖与模块责任

| 位置 | 配置和所有权 |
| --- | --- |
| 根 `.env.example` 与私有 `.env` | 按 PostgreSQL、Redis、ClickHouse、Kafka 分组。统一依赖的寻址与信任设置。Compose 内置依赖由编排派生地址，独立运行连接外部服务时由操作者填写。 |
| 模块 `config.yaml` | 实际用到的段使用 `postgresql`、`redis`、`clickhouse`、`kafka`。Go YAML 声明字段、环境变量和默认值。模块或进程按用途获得各自凭据，运行、查询及迁移权限按需分开。Web 只接收自身监听与服务器端上游地址。 |
| 连接与启动 | IO 客户端在 `bootstrap` 或独立命令的装配入口创建。每个命令加载、校验并探测自身依赖。连接代码在出现第二个真实模块调用方后再抽入共享包。 |
| 主题、表、键与保留期 | 业务模块拥有这些资源和各自的权限、索引与恢复语义。规划中的应用可以使用共享集群，新增资源和凭据在其自身交付时登记。 |

ClickHouse 公共键为 `SPX_CLICKHOUSE_URL`，Ingest 的库、写入账号及迁移账号使用 `SPX_INGEST_CLICKHOUSE_*`。Kafka 公共键采用 `SPX_KAFKA_BROKERS`、`SPX_KAFKA_SECURITY_PROTOCOL`、`SPX_KAFKA_TLS_CA_FILE`。发布者、事件写入器的认证使用各自的 `SPX_INGEST_KAFKA_PUBLISH_*`、`SPX_INGEST_KAFKA_STORE_*`。连接地址与可信 CA 可以共用。各角色只接收自己的凭据和权限。外部 Kafka 接入以数据接入记录为配置单位，数据库保存连接参数与受控凭据引用，口令通过部署侧注入。首版提供一种注入方式，示例说明如何设置与轮换。

Ingest 的 `events` 持有业务资源定义。平台事件主题、写入消费组和写入失败主题由 `SPX_KAFKA_NAMESPACE` 派生，默认使用 `spx`。已写入 ClickHouse 的 Event 永久保留，包含作为 Event 正文一部分保存的数据。首版表、列和查询均无按年龄自动删除或隐藏的规则。移除事件过期配置、命令、代码和文档入口，保留能拒绝带删除 TTL 的实库结构检查。服务端批量大小、内存预算和超时沿用经过验证的有界默认值。容量不足由运行告警和扩容处理。

平台自有 Kafka 业务主题的消息默认保留 7 天，操作者可在根 `.env` 设置 `SPX_KAFKA_RETENTION_DAYS`，值为可安全换算为毫秒的正整数天数。默认值由模块 YAML 声明，初始化和预检使用同一配置结果。初始化按主题设定 `retention.ms`、`cleanup.policy=delete`、`retention.bytes=-1`。预检回读有效值，核对内置和外接集群采用相同策略。修改已有主题时由操作者执行明确的维护步骤并回读结果。缩短前查看最老待写消息与可重放范围，更新后验证消费进度。Kafka 按日志段清理，实际可消费边界以 broker 位移为准。客户的来源主题、Kafka 内部主题及 IAM 审计、会话等其他存储沿用各自策略。 [Kafka 主题配置](https://kafka.apache.org/42/configuration/topic-configs/)

内置与外接依赖两种部署使用同一套有效配置校验。内置生成的凭据和集群标识持久保存；普通重启、安装重试和同版本恢复沿用原身份。TLS 文件、公开地址、外部连接、错误提示和样例应在各入口统一。平台只记录脱敏后的有效配置和资源身份。

## Compose 与交付范围

现阶段使用 [开发 Compose](../../../deploy/compose/compose.yaml) 和源码启动。根目录 `make compose-up` 提供正确的项目目录和配置入口。同一清单启动 Web、IAM、Console、Ingest、PostgreSQL、Redis、Kafka、ClickHouse、事件写入器及一次性初始化任务。用户准备好配置文件后，一条命令启动全栈并等待就绪。应用名单、镜像版本及摘要和默认值各在其所有者处维护。

本阶段的交付物为源码和 Compose。试制安装包已清理。

对外 HTTPS 由受控反向代理终止。沿用 Web 到 IAM 的可信来源校验，代理覆盖来源信息，IAM 仅信任登记的代理范围。Web 在缓冲 IAM、Console 请求体前施加明确的大小边界，模块仍负责本身的请求校验。设备推送继续流式交给 Ingest 限制。实际部署和回归使用同一入口核对限流、审计来源、会话和设备推送。

## 业务流程与数据模型

设备经 HTTP、Syslog 或外部 Kafka 接入。Ingest 提取字段、归一化 Event 并发布到内部 Kafka。独立事件写入进程将 Event 写入 ClickHouse，写入或按约定隔离后提交消费位移。将来检测可独立消费同一 Event 并产生 Alert。ClickHouse 是完整数据链路的必选依赖，可内置或外接。完整数据链路的备份和恢复包含 ClickHouse。

| 实体 | 权威、模型与行为 |
| --- | --- |
| 数据接入 | Ingest PostgreSQL 的接入记录决定协议、来源和绑定规则。通用字段为类型列，协议专属设置使用有大小、形状及闭合取值约束的 JSONB。接入元数据与运行态分开，区分保存、已应用、已收日志、已发布。 |
| 解析规则 | 统一为 `parsing_rule`，PostgreSQL 使用 `ingest.parsing_rules`、`ingest.parsing_rule_revisions`，外键用 `parsing_rule_id`，API 资源用 `/parsing-rules`。字段映射为 `field_mapping`。规则定义和不可变修订保留；样本最多 20 条，仅作为试算输入。常用筛选字段由规则写入同事务维护。编辑与恢复保留修订冲突检查。 |
| 标准 Event | 锁定 OCSF 1.10.0。字段、类型、单位、必填性、枚举和中英文展示来自 Ingest 字段目录，UI 或 SQL 投影引用同一权威。区分类别 `category_uid`、事件类 `class_uid` 和事件类型编码 `type_uid`。系统生成事件标识，事件发生、接收与 Kafka 来源时间按实际语义记录。未识别或失败记录的状态用于诊断，平台生成或保留的 OCSF 基础结构继续服务该路径。 |
| 事件存储 | Ingest 拥有 ClickHouse 事件表、物理投影、迁移及事件读取契约。类型列服务可证明的查询场景，完整 Event 用于回查。首版提供有权限、带时间窗、可按 ID 回查的最小事件读接口。首版表以 `toYYYYMM(event_time)` 固定划分 UTC 月分区，`event_time` 来自 OCSF `time`。月分区写入表结构，吞吐增长通过写入批量、排序、磁盘与集群容量应对。补采旧 Event 可写入相应历史月份。以代表性查询和长期容量测量验证分区与排序。 [ClickHouse 分区键指南](https://clickhouse.com/docs/concepts/best-practices/partitioning-keys) |
| 安全告警 | 检测与关联后形成的业务实体，由未来检测模块负责。本次交付到事件写入和回查，包括后续消费者可依据的 Event 契约。 |
| 审计 | IAM PostgreSQL 持有审计事实、操作者与访问控制。Ingest 管理变更与默认 outbox 同事务，IAM 按事件 ID 幂等落库。待投递队列和安全事件流各有生命周期。 |

公开 API 为每种日志入口说明确认点。HTTP `accepted` 表示平台 Kafka 已确认，超限与部分失败返回有区分度的响应；Syslog UDP 的交付语义按协议说明；外部 Kafka 确认发布后提交来源位移。事件写入消费者健康状态展示写入积压、最老未写事件及失败原因。归一化失败、写入隔离、资源不可用各有诊断入口。阻塞分区恢复要核对主题 UUID、消费组、实际可用位移和缺口范围。

### 规则与接入操作

- 普通新建规则在基础配置同排选择一个 OCSF 事件类和解析类型。事件类别分组由同一目录提供，基础事件仅作运行时诊断。已经有同源网络与认证日志覆盖的明确条件分流沿用现有定义，本次验收覆盖该路径。字段映射页专注当前类的映射。[事件类与字段映射规格](../ingest-rule-field-workflow/spec.md)
- 平台字段驱动映射。所有事件类共用语义、类型、单位及枚举一致的可映射基础字段，再叠加本类必配条件和可删除的常用字段。平台生成事件 ID 和其他由系统拥有的字段。规范的类型转换、枚举和值域来自同一契约。核心行可清空并改配，行始终在表内。缺少必配项、重复目标或不符合契约的值在相关行提示并阻止验证输出。默认值只在源字段缺失时使用。
- 规则的名称、厂商、产品、描述、事件类型、解析类型及新建样本按现有边界校验，首次进入或离开空控件时保持普通状态。重名由数据库约束和稳定错误码反馈到规则名称。解析器对单条样本的错误落在对应输入框。仅非 UTF-8 数据源设置来源编码，入口保留在第二步高级设置，真实编码用设备报文验收。[基础字段校验规格](../ingest-rule-validation/spec.md)
- 规则编辑和数据接入试算均按一个输入框对应一条日志样本处理，三行内显示，超出滚动，最多 20 条。数据接入用同一解析器试算所选规则。单类规则的提交样本须通过合规输出检查，明确分流的规则按实际覆盖与失败状态检查。已选规则不可用时保留选择并提示重试。保存时核对试算规则的修订。样本原文和仅用于试算的值由当前会话短暂持有，详情、规则修订和审计只读取其各自已持久化的数据。
- 创建、编辑和查看详情共用四步骨架。只读详情缺少原始样本时显示已保存的配置与验证摘要。两张接入管理列表默认每页 20 条，筛选、长文案及弹层行为使用现有共享组件。具体搜索范围和交互以[列表规格](../ingest-rule-field-workflow/spec.md#规则详情与管理列表)为准。系统设置沿用[现有模板对齐规格](../management-pages-consistency/plan.md#系统设置模板对齐)。

## 模块与工程边界

| 范围 | 规则与首版目标 |
| --- | --- |
| Go 进程 | `cmd` 处理命令，`config` 处理配置，`bootstrap` 装配与释放依赖。`router` 声明路由和鉴权，`handler` 绑定 DTO 与映射响应，`service` 承担用例与业务不变量。`repository` 承担持久化，SQL 放在所属模块的 `queries/`。专用运行角色和目录按真实用例创建。 |
| Ingest | 管理操作经用例层，运行态代码按接收、解析、归一化、发布和事件持久化归属。规则版本锁定、写入确认、失败重放等操作及其数据库状态由责任包维护。 |
| IAM | 管理员初始化、日常启动和凭据维护动作各有明确入口。审计写入由 IAM 用例验证与持久化。数据库使用 UTC，审计日期筛选显式接收 UTC 上下界。 |
| Console | 保持为运营查询和必要聚合的入口。完成现有 IAM 授权上下文和就绪语义收口，清理只由测试驱动的试制流及对应配置和权限。安全事件读取由 Ingest 按独立契约和权限提供。进程存活、IAM 依赖失效和业务不可用给出可区分状态。 |
| Web | 路由编排、功能目录、通用 UI、请求层和国际化词典各有稳定归属。优先收拢接入与规则工作区。规则创建、编辑、详情共用步骤、字段表示和校验约定。继续复用 List、Sheet、表单组件及现有视觉基线。 |

把适用于所有模块的长期规则沉淀在 `AGENTS.md` 及现有开发指南。行业术语锚定采用的标准版本，说明各模块的权威位置。在同一批变更中更新对外契约、数据库及字段注释、配置模板、示例、命令脚本、诊断与主文档。使用现有 lint、生成检查和实库检查复核依赖方向、权限、事件投影、SQL 和数据库所有权。首版之后继续按模块职责演进。[工程验收](plan.md#实施交接与验收)

## 验收出口

1. 空环境用全栈 Compose 启动四应用，完成登录、规则创建、数据接入、Kafka 确认、ClickHouse 写入及有权限回查。使用源码或 Compose 验证外接依赖和同版本重试。
2. 旧配置、旧命令、旧接口及试制表结构已清理。首版从空库建设。真实 Kafka 核验默认 7 天和自定义天数的有效主题策略。真实 ClickHouse 核验 UTC 月分区、永久保留和跨月补采。独立连接、最小 ACL、权限拒绝、幂等重试和恢复在真实组件验收通过。
3. 规则写入、解析预览、运行、查询、展示对同一标准字段给出一致结果。中文术语和枚举按锁定上游审核，源字段与标准字段的类型、必填、默认值和冲突提示在实际任务中验证。
4. 运维能区分配置错误、源断连、权限失败、积压和丢失窗口。损坏、不完整或与部署不符的恢复材料在写入恢复目标前被拒绝。用隔离故障演练记录事件回查、位移、恢复耗时和缺口。
5. 在公开的测试规格、数据分布、并发和故障条件下验证容量。结果支撑对外承诺。结构、验证流程和文档按四应用复核，实际未验证项按当前交付边界记录。
