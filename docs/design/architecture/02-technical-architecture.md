# 02 · 技术架构

> 实施状态：当前已落地的入口是 React Web、Go IAM/Console 和真实共享包；具体技术边界以各模块 README 为准。本文包含后续平台能力规划，未实现服务不作为本轮交付。


> **版本说明（2026-11-07 修订）**：服务清单已按仓库现状修订。`iam`、`console`、`llm-gateway` 使用 Go（Gin；`llm-gateway` 内嵌 Bifrost `core` 作为供应商适配层），Web 使用 Next.js + React + shadcn，其余 Python 服务仍为规划、尚未实现。三个已有实现的模块（Web / IAM / Console）的身份、会话、权限与存储设计以各模块 README（[IAM](../../../src/apps/iam/README.md)、[Console](../../../src/apps/console/README.md)、[Web](../../../src/apps/web/README.md)）为准；`llm-gateway` 尚未实现，其职责边界见下表与 §1.1。下文尚未实现的服务只描述规划，不代表已交付能力。


> 用大白话说：10 个自研服务 + 6 个开源组件跑在 PostgreSQL、Redis、Kafka 和 ClickHouse 上。数据从左边流进来（告警 + AI 流量两条入口），经过归并降噪变成告警和事件视图，AI 在图编排的骨架里研判，人批了以后 SOAR 执行处置回写回原系统。存储只上一个 PG（量级算过账），检索不自研发语言。

## 1. 服务清单与拆分理由

服务拆分的判据不是"功能不同"，而是以下五条之一：**独立扩容**（瓶颈维度不同）、**故障隔离**（会卡住会崩溃）、**独立变更**（改动频率不同）、**技术栈强制**、**安全边界**（高危能力单独管控）。

### 1.1 v1 全景（自研 10 组件（Python×5 + Go×4 + web 前端）；开源 6 组件）

| # | 服务 | 类型 | 语言 | 职责 | 为什么拆 |
|---|---|---|---|---|---|
| 1 | `ingestor` | 自研 | Go（Gin） | 一切外部数据的唯一入口：syslog/HTTP/Kafka 接入、格式探测、厂商模板映射为 OCSF、发布 Kafka | 改动最频繁（每接一家厂商就改），独立发版；突发流量独立扛；只收不发库，接收路径零阻塞 |
| 2 | `correlator` | 自研 | Python | D1 去重 → D2 窗口折叠 → D3 跨源关联 → 告警 + 事件视图（攻击链） | 吞吐瓶颈，纯 CPU，按实体标识分区保序扩容 |
| 3 | `agent-runtime` | 自研 | Python（内嵌 NeMo Guardrails 库） | AI 推理业务逻辑：研判 Agent（图编排骨架）、NL→查询、**guardrail 检测 API**（ai-policy 的模型类检测调这里）。**模型调用本身经 `llm-gateway`** | **LLM 有 1/4 概率超时/无结果**【官方文档·腾讯实测】，必须和管线故障隔离——部署时独立容器 |
| 4 | `soar` | 自研 | Python | **通用 workflow/playbook 引擎宿主**（orchestrator 库）、预案库、审批状态机（持久化暂停）、高危动作执行、按上游原生 ID 回写；通知（邮件/IM/工单）是 governed action | 安全边界：Agent 提议 / SOAR 执行的权限分界 |
| 5 | `ai-policy` | 自研 | Python | AI 安全策略大脑（独立 PDP，SpiceDB/Cerbos 同款形态）：规则、ext_authz 决策、事件回流、管理 API。**检测分两层**：规则类（正则/关键词/schema）内存匹配走同步路径（亚毫秒）；模型类（语义级注入/越权）异步调 agent-runtime 的 guardrail API（NeMo 库内嵌于彼） | 独立 PDP 是行业标准形态；同步路径只有规则不阻塞客户流量 |
| 6 | `iam` | 自研 | Go（Gin） | 账号、密码、Session、角色与扁平权限、身份审计。已交付；MFA、SSO（OIDC/SAML）、SCIM、公开注册、对象 ACL 未实现 | 身份是核心攻击面，被所有服务验签；内置而非独立 IdP，小规模下拆开只有同步与一致性成本 |
| 7 | `console` | 自研 | Go（Gin） | 安全运营业务后端：案件、三队列工作台、运营查询与必要的跨域只读汇总。当前仅提供身份上下文与带持续授权检查的 SSE；案件与工作台尚未实现 | 安全运营业务归属 + 高危操作边界；不作为全平台 API 的强制中转站 |
| 8 | `web` | 自研 | TypeScript / Next.js | 前端 | 技术栈强制 |
| 9 | `scheduler` | 自研 | Python | 全部**平台级**定时任务的唯一入口：情报拉取、报表、蜜标巡检、供应链扫描 | **基础设施组件（cron 哲学：简单、稳定、永不失败）**：任务代码内声明 + DB 持久化 + 分布式锁单实例；与 playbook 的 schedule 触发器分层——用户业务流定时归 orchestrator，平台心跳归这里，基础设施不依赖业务引擎 |
| 10 | `llm-gateway` | 自研 | Go（内嵌 Bifrost `core` SDK） | 平台自身的模型出口：供应商凭据的唯一持有者、模型清单自助管理、别名到真实模型的解析、重试与降级、用量归因 | 安全边界（持有全部供应商密钥）+ 故障隔离（LLM 会超时）+ 独立变更（供应商适配最频繁）+ 技术栈强制（多语言调用方需要 HTTP 边界） |
| 11 | `ai-gateway` | **开源** | agentgateway（Rust） | 哑数据面：用户 AI 流量（LLM+MCP）的 inline 治理，决策回调 #5 | 只依赖 xDS + ext_authz 两个稳定协议，升级不被绑定 |
| 12 | `postgres` | **开源** | PostgreSQL 16 | 业务主存储：身份、权限、告警、案件、调查台账、配置、审计 | 需要事务与外键的业务对象 |
| 13 | `redis` | **开源** | Redis 7 | 去重窗口、限流、会话缓存 | 需要 TTL 的高频读写 |
| 14 | `kafka` | **开源** | Kafka 4.2.2（KRaft，无需 ZooKeeper） | 削峰与回放：采集到关联之间的缓冲 | 峰值流量需要落盘而非占内存；消费方故障后要能重放 |
| 15 | `clickhouse` | **开源** | ClickHouse 26.8 LTS | 大流量遥测查询：原始日志、归一化事件、狩猎与分析 | 列存 + 时间分区，支撑 AI 的并发多条件跨时间查询 |
| 16 | `object-storage` | **开源** | MinIO / S3 兼容 / 本地 FS | raw payload、Parquet 归档 | raw 永不进主表 |

### 1.2 每个模块的技术架构

十一个模块分三类：**已交付的三个 Go/Web**、**规划中的五个 Python + 一个 Go（ingestor）**、**一个开源数据面**。下面只写"用什么技术、连什么存储、跟谁说话"，不写字段和接口细节。

```
                        ┌──────────── 已交付 ────────────┐
  浏览器 ──▶ web(Next) ─┬─▶ iam(Go) ──┬─▶ PostgreSQL
                        │             └─▶ Redis
                        └─▶ console(Go) ──▶ iam（服务凭证+用户上下文）

                        ┌──────────── 规划中 ────────────┐
  数据源 ──▶ ingestor(Go) ──▶ Kafka ──▶ correlator(Py) ──┬─▶ PostgreSQL（告警）
                                                          └─▶ ClickHouse（遥测）
                              correlator ──▶ agent-runtime(Py) ──▶ llm-gateway(Go) ──▶ 供应商
                              agent-runtime ──▶ soar(Py) ──▶ 上游系统回写
                              scheduler(Py) ──定时──▶ 各模块
  用户AI流量 ──▶ ai-gateway(开源) ──回调──▶ ai-policy(Py)
```

#### 已交付

| 模块 | 技术栈 | 存储 | 对外接口 | 依赖谁 |
|---|---|---|---|---|
| `iam` | Go 1.27 + Gin 1.12；**sqlc 1.31 生成类型化查询**、pgx v5 做驱动（GORM 仍在移除中，见 [数据访问层计划](../../plans/sqlc-data-layer/plan.md)）；SCS 管 Session；Argon2id 存密码；Cobra 管命令；Goose 管迁移 | PostgreSQL（自己的表 + 会话）<br>Redis（限流） | `/api/v1/iam/*`：用户接口走 Cookie + CSRF；服务接口走服务凭证 | 无（它是最底层） |
| `console` | Go + Gin；**没有数据库** | 无自有存储 | `/api/v1/console/*`：全部请求先向 IAM 换授权结论 | `iam`（经 `iamclient`） |
| `web` | Next 16 + React 19；next-intl 双语；TanStack Query 取数；Zod + RHF 管表单；Axios 请求；Tailwind 4 + shadcn | 无（浏览器端状态） | 页面 + 同源窄代理 `/api/v1/{module}/*` | `iam`、`console`（服务端转发） |

**为什么 `console` 没有数据库**：它当前只做"验证身份与授权后的 SSE"。等案件和工作台真正实现时，再按模块自己的表加。AGENTS 里写死了这条：模块拥有自己的配置、启动和表——不预先建空库占位。

**为什么 `iam` 的数据访问走 sqlc 而不是 ORM**：SQL 是唯一事实源，`sqlc generate` 产出类型化查询与行结构，列名、类型和参数在编译期受检查；schema 直接取 goose 迁移，不维护第二份 DDL；生成物入库并由 CI 的 `sqlc diff` 拦截漂移。这里的取舍与依据见 [数据访问规范](../../development/data-access.md) 与 [数据访问层改造计划](../../plans/sqlc-data-layer/plan.md)。GORM 仍在迁移期（会话、用户、列表、审计、维护尚未迁移），最终会被移除；底层始终是 pgx 连接池，迁移仍由 Goose 显式执行，不做自动建表。

#### 规划中（ingestor 与 Python 五件）

这六个服务**还没有代码**，技术栈只定到"语言 + 关键库"这一层：

| 模块 | 语言/关键库 | 存储 | 跟谁说话 |
|---|---|---|---|
| `ingestor` | Go + Gin | Kafka（产出）<br>PostgreSQL（connectors 注册表） | 对外收数据；对内发 Kafka；不写业务数据 |
| `correlator` | Python | PostgreSQL（告警/事件视图）<br>ClickHouse（遥测）<br>Redis（去重窗口） | 消费 Kafka；产出告警 |
| `agent-runtime` | Python + NeMo Guardrails | PostgreSQL（Ledger） | 调 `llm-gateway`；读告警 |
| `soar` | Python + orchestrator 库 | PostgreSQL（预案、审批状态） | 执行处置；回写上游 |
| `ai-policy` | Python | 内存规则 + Redis | 被 `ai-gateway` 回调；异步调 `agent-runtime` |
| `scheduler` | Python | PostgreSQL（任务表 + 分布式锁） | 定时触发各模块 |

#### 开源数据面

| 组件 | 它干什么 | 我们不做什么 |
|---|---|---|
| `ai-gateway`（agentgateway，Rust） | 拦用户的 AI 流量，问 `ai-policy` 要不要放行 | 不自研流量转发；只依赖 xDS + ext_authz 两个协议 |
| `llm-gateway`（自研 Go，内嵌 Bifrost `core`） | 我们自己调模型的唯一出口 | 不用 Bifrost 的 `bifrost-http`（它带自己的身份体系） |

#### 一条贯穿全局的规矩

**模块之间只通过 HTTP 契约或消息队列通信，不读对方的表、不导入对方的 internal 包。** 已交付的两个 Go 服务就是这样：`console` 只拿 `iamclient`，不碰 IAM 的表和内部实现。

**两个容易混淆的区分**：`ai-gateway` 管的是**用户**的 AI 流量（防护对象），`llm-gateway` 管**我们自己**调模型的流量（内部出口）——方向相反不能共用；`soar` 与 `agent-runtime` 的分界是"想"和"做"——高危动作不能跑在 AI 进程里。

**语言版图**：当前 Web 使用 TypeScript/React，IAM、Console 与规划的 llm-gateway 使用 Go，根 Go module 统一管理服务及共享包。后续 AI 能力可按实际生态选择 Python；跨语言依赖通过公开契约隔离，不因语言选择增加不存在的服务或生成多套协议真源。Python 模块调用模型统一经 llm-gateway 的 HTTP 接口，不内嵌 Go 库，也不各自持有供应商凭据。workflow/playbook 等后续服务的选择由各自需求方案确认。

**组件 / 角色 / 镜像**：每个模块是一个独立的部署单元，独立启动（Go 模块由 `ARG APP` 参数化构建，共用一个 Dockerfile；Web 独立执行 `next build`）。**不使用"一个镜像 + 角色开关启动所有服务"的多角色模式**——那会让故障隔离和独立扩容失效。当前交付的 Go 模块为 `iam`、`console`，规划中的 `llm-gateway` 同样通过 `ARG APP=llm-gateway` 构建，不新增 Dockerfile

## 2. 数据流：以数据流入为主轴

架构图从数据流入开始，用户操作是旁挂的控制平面——数据永远不经过人。

```
══════════════ 数据源（数据从这里流入）══════════════

   告警数据源                            用户 AI 流量（防护平面 · inline）
   EDR · WAF · SIEM · 云安全中心           用户 LLM 应用 / AI Agent
   webhook · syslog · API 拉取            LLM API 调用 · MCP 工具调用
        │                                      │
        │                               ┌──────▼───────────────┐
        │                               │     ai-gateway       │
        │                               │ （agentgateway·Rust） │
        │                               └───┬──────────┬───────┘
        │                           决策回调│          │ 放行流量
        │                               ┌───▼──────────▼────┐
        │                               │     ai-policy     │
        │                               │ 注入检测·DLP        │
        │                               │（内嵌 NeMo 库）    │
        │                               └─────────┬─────────┘
        │                                         │ 拦截 = 安全事件
        │                                         │（与 EDR 告警同链路）
        ▼                                         ▼
════════════ 数据处理主链路（自上而下）══════════════
  ┌─────────────────────────────────────────────────────┐
  │ ① ingestor —— 接入 · 归一化                           │
  │    OCSF 归一化 · 形状判别 · L0/L1 校验                  │

                           │ 告警 + 事件视图
  ┌────────────────────────▼────────────────────────────┐
  │ ③ agent-runtime —— 研判（图编排骨架 + 受限 LLM）         │
  │    知识前置过滤 → 假设驱动调查 → 证据级判定 → 三值结论      │
  │    触发：Case 事件 / 页面手动 / scheduler 定时            │
  └────────────────────────┬────────────────────────────┘
                           │ 结论 + 置信度 + 证据（Ledger 留痕）
  ┌────────────────────────▼────────────────────────────┐
  │ ④ 案件 Case（PostgreSQL · 状态机）                      │
  │    新开 → 研判中 → 待处置 → 已闭环                       │
  └────────────────────────┬────────────────────────────┘
                           │ 提议（默认人审批）
  ┌────────────────────────▼────────────────────────────┐
  │ ⑤ soar —— 处置                                        │
  │    资产爆炸半径门控 → 审批 → 幂等执行 → 上游原生 ID 回写    │
  └─────────────────────────────────────────────────────┘

════════════ 控制平面（页面操作，旁挂不穿流）════════════
   用户 → web → 同源HTTP入口 ─┬─ iam：身份、会话、角色与权限
                              ├─ console：案件、运营工作台与查询汇总
                              └─ 其他模块：按业务归属接入
   console 按自身业务需要调用其他模块；不作为全平台API的强制中转站。
   工作流、Agent和审批的最终状态与执行规则归对应模块。
   scheduler ──定时──▶ ① API 拉取 · ③ 定时任务 · 蜜标/情报/扫描
```

三条设计要点：

1. **两条数据源的汇合点在 ①**——`ai-policy` 拦下的注入事件回流 `ingestor`，从此和 EDR 告警走完全相同的链路。"防护对象 = 运营对象"在架构上就这一条线。
2. **跨阶段连接全靠队列不靠调用**——①→② 走 Kafka，②→③ 走 Case 事件；任何一级慢了或挂了，上游照常摄入，恢复后接着跑。
3. **`worker` 和 `agent` 必须分进程不是洁癖**——LLM 卡住会阻塞去重；且两者扩容维度完全不同（CPU 密集 vs 网络等待密集）。

### 2.1 模型出口：所有调模型的动作都经过 llm-gateway

```
  agent-runtime ─┐
  ai-policy     ─┼──▶ llmclient（类型化客户端）──▶ llm-gateway ──▶ 供应商
  console       ─┘        用角色别名                 唯一持有密钥
  （未来模块）   ─┘      triage/investigate           重试·降级·用量

  管理面：web ──▶ llm-gateway  /api/v1/llm-gateway/providers（增删改查+测试连通）
```

**为什么必须有这一层**：

| 问题 | 各自直连供应商的后果 |
|---|---|
| 密钥管理 | 密钥散落在 N 个部署单元，轮换要改 N 次，审计看不到全貌 |
| 策略一致性 | 超时、重试、降级每个模块各写一遍，必然漂移 |
| 成本归因 | 回答不了"哪个用户、哪个功能花了多少 token" |
| 换供应商 | 每个调用方都要改代码 |

**为什么不用现成的网关服务**：LiteLLM 是 Python 代理，存在内存增长与升级迁移风险；Bifrost 的 `bifrost-http` 会引入它自己的身份体系，与我们的 IAM 重复。我们只嵌入 Bifrost 的 `core` 库——它没有身份概念，`schemas.Account` 三个方法交由我们从自己的表读取，因此**不会形成第二套账户体系**。证据见 [04 §7](04-research-references.md)。

**与 ai-gateway 的区别**：`ai-gateway` 管**用户**的 AI 流量（防护对象，要被检测）；`llm-gateway` 管**我们自己**调模型的流量（内部出口）。方向相反，不能共用。

## 3. 数据模型

### 3.1 核心实体

```
assets            资产（含 AI 资产）+ 指纹；关键性等级（处置门控用）
alerts            告警：OCSF 2004 结构 + 实体抽取 + ATT&CK + chain 元数据
                  + source_refs[]（上游原生 ID 映射，一对多）
                  + aggregation_evidence（上游合并探测三档置信）
incident_views    事件视图：Redis 滚动 TTL（不建重表）+ 告警上的 chain 字段
cases             案件（OCSF 2005）：状态机 + case_tasks + case_timeline
investigations    调查 Ledger：Run / Event / Artifact（prompt、工具调用、引用全量）
institutional_memory  机构记忆：结论沉淀 + 分析师纠正（reason 必填）+ 用户直录
rule_proposals    规则建议：propose → review → eval-gated → promote
shadow_decisions  影子模式记录：从第一天攒，授权的依据
entities          实体档案（IP/账号/主机/hash）：画像、历史、关系（agent 的上下文底座）
```

**三条贯穿性设计**：

1. **业务表用不可变 UUID 主键，按时间 + 实体标识分区**（模型见 §3.4）。这是"架构上支持未来多集群"的真正含义——不是现在就上多集群，而是现在不做未来拆不动的事：届时按时间窗口或 hash 拆分都不用改主键结构。不引入额外的范围列。
2. **保留策略 = 工作记忆模型**（详见 §6.1）：归一化告警 90 天滚动窗口（按天分区过期自动清）、raw payload 7–30 天可配、事件视图 TTL 滚动；**案件、调查 Ledger、机构记忆/影子决策永久**（大脑的产出与经验）。
3. **证据自包含原则（由 2 推出，防止 90 天清理割裂永久案件）**：案件和 Ledger 在结案时保存**证据快照**——研判依据的关键字段、source_refs、原始日志摘要冗余进 Ledger（它本来就存 prompt/工具调用/返回全文，天然自包含）。告警行过期清理**不影响**任何永久对象的完整性：案件回看证据读快照、处置回写读案件上冗余的 source_refs、影子统计读永久的 shadow_decisions 表。一句话：**告警是可再生的原料，案件和 Ledger 才是账本。**

### 3.2 归一化：OCSF 2004，不追全量映射

**【官方文档】** OCSF v1.9.0（当前稳定版）2024-11 捐给 Linux Foundation，2026-06 成为 ITU 国际标准；`security_finding`(2001) **已废弃**（since 1.1.0），新项目直接用 `detection_finding`(**2004**)。

四个必抄的机制【官方文档·OCSF 2004 定义】：

| 机制 | 作用 |
|---|---|
| `count` + `start_time`/`end_time` | 上游聚合语义的唯一标准字段——**必须读进内部模型** |
| `unmapped` | 映射不上的字段全塞这里，一条不丢——半年后排障的救命稻草 |
| `vendor_attributes` | "厂商给的值"和"我改过的值"分开存——可解释 AI 的刚需 |
| `observables[]` + `evidences[]` | 实体集中列出带路径引用，关联/富化/情报都从这里读 |

归一化分四层：**L0 最小必需集**（缺了进隔离区不进主表）→ **L1 通用实体**（actor/user/process/file/network + ATT&CK ID）→ L2 厂商专属（按需）→ L3 raw 永存。工作量比例约 7:2.5:0.5。

**六条归一化工程约束**（验证要求见 04 §4）：

1. 时间解析失败 → `null` + warning，**绝不回退 `now()`**
2. 缺失就是 `null`，不写 `"none"` 哨兵值
3. 解码顺序 UTF-8 strict → GB18030 → replace，**编码记在事件上**（国内设备大量 GBK）
4. `actor.kind` / `outcome` 判断不出就是 `unknown`，不许猜
5. 字段路径支持数组下标 + **填充率报表**（映射静默失效是常态）
6. 归一化质量门禁进 CI：填充率、warning 计数看板、schema 校验、每连接器 5–10 条回归样本

### 3.3 降噪合并：三层独立可解释

厂商合并解决"别刷屏"（单产品、单规则、同实体）；我们的合并解决"研判对象唯一"（跨产品、跨厂商、跨时间）。分层是因为混在一起就永远回答不了"这两条为什么被合并了"——用户和分析师一定会问。

| 层 | 干什么 | 键 | 输出 |
|---|---|---|---|
| D1 精确去重 | 重复投递（重放/重试/多路采集） | 同源 + external_id + 关键字段 hash | 丢弃，计数 +1 |
| D2 同源窗口抑制 | 同规则对同实体反复刷 | 同源 + rule + 主实体 + 时间窗（5–60min） | 折叠，保留 count 和时间范围 |
| D3 跨源实体关联 | 多产品告警串成一个事件 | 共享实体（IP/账号/主机/hash/域名）≥2 | 事件视图 + 关联理由（必须可解释、可一键拆开） |

**上游是否已合并判断不出来**——查遍 OCSF/ECS/ASIM/UDM/ASFF/Sentinel/QRadar 没有任何标准有 `is_aggregated` 字段【官方文档】。落地方式是接入期"合并指纹探测"报告（计数字段、ID 稳定性、时间戳对齐痕迹、上层对象 ID 七项探测），输出**三档置信度**而非布尔值：已确认聚合 / 疑似聚合 / 未观察到迹象（≠未聚合）。

**分区保序**：队列分区键必须与关联键同构，统一使用实体标识（src_ip → device → user → 域名），且 entity 解析顺序必须与关联键**同一份代码**——否则同一实体的告警散在不同分区被不同副本消费，序列拼错、事件一分为二，而且看起来一切正常。无实体事件回退 event_id（回退固定常量会造成热分区）。

### 3.4 身份、角色与权限（IAM 体系）

**为什么是一个 iam 而不是拆开的用户系统/权限系统/认证中心**：IAM（Identity and Access Management，身份与访问管理）是领域名称，不是微服务架构专属词——它指的就是"认证 + 用户目录 + 授权"合并的一个领域。大厂拆成独立的用户中心/权限中心是被规模（几十个系统、几万员工）逼出的**部署拆分**，不是领域本该拆分；领域上认证与授权共享同一份用户目录，小规模下拆开只有同步与一致性成本。业界常态是内置合并（Grafana/GitLab/Django/TheHive 均单体内置；Keycloak/Zitadel 本身就是合并一体的产品）。

**为什么没有多租户与数据隔离层**：产品是一台设备、一个安全运营团队、一套权限，不是 SaaS 多客户。按客户隔离在这里没有对应业务，硬加一层会让每个请求先解析范围、每个查询先拼过滤条件。因此模型里没有租户表、没有作用域列、没有会话级的范围变量，也没有由此派生的 RLS 策略。

**授权模型**：只有一条路径，`用户 --user_roles--> 角色 --role_permissions--> 权限`。角色是全局对象（名称唯一、内置标记 `builtin`），用户直接持有角色；一个用户可以持有多个角色，有效权限取并集。多角色是刻意的：现实中同一个人常身兼多职，单角色会逼出"为每种组合建一个角色"的组合爆炸。

**权限目录扁平**：7 个权限键（`iam.users.read` / `iam.users.manage` / `iam.users.roles` / `iam.users.reset` / `iam.roles.read` / `iam.roles.manage` / `iam.audit.read`），没有 platform 与业务范围两级，也没有 `scope` 字段。权限在代码中版本化定义（`internal/authorization/permissions.json`），启动时同步成数据库投影；语义变更没有配套迁移时启动失败。

**内置数据**：权限目录、超级管理员角色（`builtin=true`，持有全部权限）与配置管理员账号（`configured=true`）在启动时按配置幂等写入；内置角色只读，配置管理员不可删除、不可停用、不可在页面改密。超管身份就是"持有内置超级管理员角色"这一条数据，没有 `is_super_admin` 布尔列。

**iam 的职责边界（标准 PDP/PEP 分层）**——所有权限的**定义、判定、管理**收敛于 iam（策略决策点），**执行**分布在三个检查点：

```
┌────────────── iam（唯一权威源：认证 + 目录 + 授权 + 管理 + 上下文分发）──────────────┐
│ 认证：本地账号密码（Argon2id 哈希·登录锁定·会话/refresh token 轮换）· MFA(TOTP)      │
│       · OIDC/SAML 对接用户已有 IdP（飞书/钉钉/Zitadel/Keycloak 均可插拔）            │
│ 目录：用户 · 角色 · 权限目录 · SCIM 同步                                             │
│ 授权：RBAC 策略 · 扁平权限点定义（iam.users.read / iam.roles.manage / …）            │
│       · 菜单可见性 = 权限点的派生映射（前端登录后按能力投影渲染菜单）                  │
│ 管理：用户管理 · 角色与权限分配的管理 API——Web 管理页经同源入口调用它                 │
│ 分发：凭据签发与会话分发（浏览器会话/服务间 JWT/API Token），全系统唯一验签点          │
└──────────────────────────┬────────────────────────────────────────────────┘
                           │ 会话 / 权限点声明
        ┌──────────────────┼──────────────────┐
        ▼ 执行点①API       ▼ 执行点②数据        ▼ 执行点③前端
        每个服务的中间件     资源模块校验归属      web 按能力投影渲染
        验签 + 权限点校验    （事务 + 外键约束）    菜单与按钮
```

**权限校验分层**：

| 层 | 做什么 | 不做什么 |
|---|---|---|
| API | 路由声明所需权限键，向 iam 换决定；拒绝即 403 | 不从请求参数取 action，不自行拼一套角色判断 |
| 数据 | 资源所属模块在查询和事务中校验真实归属（属主、状态、关联） | 不把"有权限"当成"这条数据归你"，不查其他模块私表 |
| 前端 | 按能力投影渲染菜单与按钮 | 不把隐藏按钮当授权，不缓存"允许"结果 |

**三条总线（后来者改不错的机制）**：

| 总线 | 机制 | 新开发者的接入姿势 |
|---|---|---|
| 上下文总线 | iam 中间件验签 → RequestContext{user_id, session_id, roles, permissions} 注入 | 业务代码只取上下文，不碰认证实现 |
| 数据访问总线 | 业务查询自己带归属条件，事务保证状态与审计同提交 | 新表按所属模块的归属规则查询，没有全局注入的过滤条件 |
| 事件总线 | Kafka，实体标识作 partition key | 新事件带实体标识，消费者按上下文处理 |

**自举**：管理员来自启动配置（`bootstrap.username/password`），启动时幂等写入数据库并授予内置超级管理员角色；没有安装页面，也没有一次性密码。MFA、SSO（OIDC/SAML）与 SCIM 尚未实现；对接设计走标准协议而不是私有实现，因此未来换用 Zitadel/Keycloak 这类完整企业 IdP 时不需要改业务模块（方案 B 保留为升级路径）。

## 4. Agent 编排：图编排骨架 + 受限 LLM

海外五种路线对比后收敛的选型：

| 路线 | 代表 | 评估 |
|---|---|---|
| 自由递归推理 | Dropzone | 深，但一致性靠工程补 |
| **图编排 + 受限 LLM** | **Prophet** | "一致且确定，而不是自由形式的 LLM 链"——可靠可审计 ✅ |
| 对等单职责 agent 群 | Exaforce / Microsoft / Google | 边界清晰可分别发权 ✅ |
| 编排者+执行者 | Torq Socrates | 灵活但复杂度高 |
| 模仿人类分析师 | Radiant（已被 Cribl 收购） | — |

三方证据收敛：Prophet 用产品验证了图编排【实测】；腾讯实测单 agent 成功率仅 75%【官方文档】；学术评测 AIDA 证明**结构比模型重要**（四角色独立上下文 F1 从 0.371–0.744 拉到 0.958，去掉 Judge 掉到 0.895，9B 小模型也能跑 0.952）【论文·arXiv 2610.10608】。

我们的研判流程是一张可配置的图，LLM 只出现在边界清晰的节点里：

```
┌─────────────────────────────────────────────────────────────────┐
│                     研判流程图（图编排骨架，确定性）                  │
│                                                                 │
│  [知识前置过滤]──▶[假设生成]──▶[逐假设取证]──▶[证据级判定]──▶[聚合结论] │
│   规则/知识库      列出竞争性     图决定查什么、    每条证据独立     │
│   挡掉明确噪声     解释(受限LLM)  按实体档案组查询   verdict(受限LLM) │
│                                                                 │
│   ──▶[groundedness 门禁]──▶[三值结论 + 置信度 + Ledger]──▶[三队列]  │
│                                                                 │
│  图节点可配置；LLM 节点声明 bounded task 类型；                     │
│  复杂案件升级 → 深度调查模式（对话式：人驱动多轮、AI 执行每轮推理，全程 Ledger）│
└─────────────────────────────────────────────────────────────────┘
```

- **假设驱动**【实测·Dropzone】：先列"这条告警为什么触发的所有竞争性解释"，每个假设对应一组查询，逐一证实/排除/引出新问题——研判是科学方法不是流水线。
- **证据级 → 告警级两级判定**【实测·Intezer】：每条证据先有独立 verdict，再聚合成告警结论——可独立审计，正好喂给 groundedness 门禁。
- **Schema 语义**【论文·arXiv 2408.02442】：输出字段顺序 `evidence[] → reasoning → verdict → confidence`——JSON 模式下 GPT-3.5 有 100% 概率把 answer 排在 reason 前面，"先猜后编理由"，物理顺序能堵。
- **按岗位拆 agent**【实测·Microsoft Copilot 套件】：triage / hunt / deep-dive 三岗位，自治级别独立配置——和影子模式互补（微软按岗位发权，我们按告警类别发权）。
- **成本三道闸**【代码/官方文档】：①同 `dedup_key` 只对 leader 调 LLM、follower 复用结论②知识前置过滤（见 01 §5.2）③平台级 token 配额硬顶（阿里云"每主机每日 20 条 AI 研判"同款思路——用配额逼自己把 token 花在值得的告警上）。

## 5. AI 可靠性：六条硬约束

先接受现实水位——**当前 agent 化安全分析的真实水平是 60–75%，不是 95%**。三方独立证据：腾讯生产环境 75%【官方文档】、微软 ExCyTIn-Bench 最好模型 reward 0.606【论文】、SIABench 深度调查 40–60%（但 TP/FP 二分类 96–98%）【论文】。

| # | 约束 | 依据 |
|---|---|---|
| 1 | **三值结论**，`insufficient_info` 是一等公民（独立队列独立 SLA） | 阿里云官方即三值；火山三队列同构 |
| 2 | **工具返回三态**：`ok_empty` / `error` / `not_supported`，空结果不得作为关单依据 | ALERT-BENCH：空结果导致 4/5 方法漏掉 ≥88% 攻击告警 |
| 3 | **groundedness 门禁**：确定性实体比对（IP/hash/CVE/域名），score < 0.75 只许降级不许自动关单；门禁必须接在生产链路不只评测 | 生产执行路径必须调用门禁，CI 验证实际调用关系和失败分支 |
| 4 | **禁止同上下文自审**；要审就独立上下文或换模型 | Self-Refine 改对 16 改错 79；CoVe 改对 25 改错 132 |
| 5 | **ATT&CK 只做候选集分类**，不许开放生成 technique ID | CTIBench 开放抽取 macro-F1 仅 0.3108 |
| 6 | **处置绑定实体 + 上游原生 ID + 默认人审**，三缺一不执行 | 阿里云/火山/CrowdStrike 一致做法 |

配套：**"低慢攻击是 AI 研判的系统性盲区"**【实测·Reddit 一线评价 MS Phishing Triage Agent 为 "mid"】——这条要显式写进能力边界，`insufficient_info` 队列就是为它存在的。

## 6. 存储与检索

### 6.1 存储：大脑的工作记忆，不是数据资产

存储的角色由产品定位直接决定：SecPlexus 是外挂大脑，**原始告警的 system of record 是用户自己的 SIEM**（他们本来就有，而且存得比我们好）——我们不当第二档案馆。平台仍需保留运营闭环所必需的数据，分界线如下：

> **大脑的产出和经验永久，大脑的输入（别人的告警）只留工作窗口。**

**为什么需要持久化运营数据**。仅在收到告警时执行一次流程，无法支持后续关联、检索和审计。平台需要满足：

1. **跨厂商关联是大脑的核心职能，而它必须有地方存东西。**"EDR 说执行、防火墙说外连、身份说异常登录是同一次攻击"——这个串联只有中立层能做（厂商各自只看到自己）。告警不落地，"关联"就退化成每次研判时模型现场去各家查——这正是 01 §1.3 批评 AI 助手的原话（"同一实体 3 分钟前的相关告警要靠模型自己在会话里查"）。选不存储等于亲手把自己做回助手。
2. **经济性**。腾讯实测链路 17 万 → 1834 → 42：先归并再研判。没有预合并，10 万条/天全部进 LLM，成本差两个数量级。
3. **记忆飞轮需要历史**。机构记忆、影子模式按类别攒正确率、检出率统计，全部建立在告警历史存在之上。
4. **回写需要锚点**。处置回写用上游原生 ID，`source_refs` 必须持久；没有存储就没有案件实体，没有案件就没有审批/闭环/审计。

**保留策略（工作记忆模型）**：

| 数据 | 角色 | 保留 |
|---|---|---|
| 归一化告警（PostgreSQL） | 大脑的输入 | **工作记忆：默认 90 天滚动窗口（可配），按天分区过期自动清理**。要考古？跳回用户自己的 SIEM 查，我们保留跳转链接。案件的完整性不依赖告警行存活——证据快照自包含（见 §3.1 第 3 条） |
| 原始日志 / 归一化事件（ClickHouse） | 大脑的原料，含用户直接投递的日志 | 按天分区 TTL 滚动过期；量由用户决定，不是我们的资产 |
| raw payload | 归一化回放依据 | 7–30 天可配 |
| 事件视图 | 研判分组 | TTL 滚动，可重建（不变） |
| **案件 Case** | 大脑的产出 | **永久** |
| **调查 Ledger（含证据快照）** | 大脑的推理记录 | **永久** |
| **机构记忆 / 影子决策** | 大脑的经验 | **永久** |
| **实体档案 entities** | 大脑的知识（IP/账号/主机的画像与关系，研判上下文底座） | **永久**（画像可从新告警持续刷新） |

### 6.2 存储分工：PostgreSQL 存业务对象，ClickHouse 存遥测

**一句话**：会改的东西放 PostgreSQL，只会追加的东西放 ClickHouse。

```
                      写一次，之后不停被改
   告警 / 案件 / 台账 ────────────────────▶  PostgreSQL
   （状态、指派、优先级、关联案件）             事务 + 外键 + 行级更新
                                              量小、可改、要一致

                      只追加，永不修改
   原始日志 / 归一化事件 ──────────────────▶  ClickHouse
   （狩猎、分析、AI 多条件跨时间查询）           列存 + 时间分区
                                              量大、只读、要好查

   削峰缓冲 ───────────────────────────────▶  Kafka
   （峰值不占内存，消费方挂了能重放）

   去重 / 限流 / 会话 ─────────────────────▶  Redis
   （要毫秒级 + 自动过期）

   大对象 ─────────────────────────────────▶  对象存储
   （raw 永不进主表）
```

判断依据只有两条：**这个对象会不会被改？量的增长是几倍还是几个数量级？**

| 存储 | 存什么 | 判断依据 |
|---|---|---|
| **PostgreSQL** | 身份、权限、**告警**（含状态/指派/优先级/案件关联）、案件、调查台账、机构记忆、实体档案、规则与配置、审计 | 需要事务、外键、行级更新；量级在千万到亿级可承受 |
| **ClickHouse** | 原始日志、归一化事件、狩猎与分析所需的大流量遥测 | 只追加、不修改；单次查询要跨时间范围扫多条件、并发高 |
| **Redis** | 去重窗口、限流计数、会话缓存 | 需要 TTL 的高频读写 |
| **对象存储** | raw payload、Parquet 归档 | 大对象，永不进主表 |
| **Kafka** | 采集到关联、关联到研判之间的流转 | 削峰（峰值不占内存）、消费方故障后可重放 |

#### 为什么告警放 PostgreSQL

| 理由 | 具体说明 |
|---|---|
| **告警要改** | 状态流转（new→triaged→investigating→resolved）、指派、优先级、关联案件——这些都是行更新 |
| **改状态和写审计必须原子** | AiSOC 的代码注释原文："the alert change and the record of it land together or not at all"。ClickHouse 没有事务 |
| **要外键** | `case_id` 指向案件、`assignee_id` 指向用户。ClickHouse 没有外键 |
| **要表约束** | 唯一键、外键与 CHECK 在 PG 强制执行；ClickHouse 只有表引擎级约束 |

**别的方案为什么不行**：

| 方案 | 为什么不行 |
|---|---|
| 告警也放 ClickHouse，用轻量 UPDATE | ClickHouse 的 UPDATE 是异步生成 patch part，高频单行改会产生大量 patch，merge 压力大；且没有事务和外键，"改状态+写审计"无法原子 |
| 告警只追加新版本（Matano 式） | 查询时每条告警要取最新版本，复杂度转移到了每次读；且同样没有事务 |
| 全放 PG，不引入 ClickHouse | 用户可能直接投递原始日志（我们无法约束输入形态），日志量比告警大 2 个数量级，PG 扛不住 |

**证据**：nano（README 原文 "ClickHouse stores the logs. Postgres holds metadata like rules, alerts, users, dashboards, audit"）、SigNoz（关系库 "exclusively for storing metadata and control-plane information"）、AiSOC（告警在 PG 且频繁 UPDATE，见 `services/api/app/api/v1/endpoints/alerts.py`）三个项目同一分工。详见 [04 §3.1](04-research-references.md)。

**告警放 PG 不丢查询能力**：告警表按时间分区，并按实体标识 + 时间建索引，AI 的"多条件 + 跨时间范围"查询在 PG 上一样能跑。真正需要 ClickHouse 的是"原始日志级别"的量，不是降噪后的告警。

**ClickHouse 的适用前提**：用户的输入不一定是告警，也可能直接是原始日志，我们无法约束。原始日志由 ClickHouse 承载；平台自身不做厂商数据的第二档案馆，遥测按工作窗口滚动过期。

算账（告警在 PG，遥测在 CK）：

| 数据 | 估算 |
|---|---|
| 归一化告警 | 降噪后 10 万条/天 × ~1KB × 90 天 ≈ **9–27GB** |
| 原始日志（若用户提供） | 按实际量单独评估，走 ClickHouse，按天分区 TTL |
| 行业均值参考 | 约 3,000–4,500 条告警/天（04 §5.1），10 万/天是我们的设计容量 |

说明：以上为设计容量，需在实现时通过索引、分区和真实负载验证。若告警量增长到 PostgreSQL 无法承受（单一部署 > 100 万条/天），首先引入的是 Panther 式的拆分——告警核心状态留在 PG、告警内容外置到 ClickHouse——而不是把整张告警表迁走。

现在必须做对的三件事（否则以后要重写）：

1. **raw 永不进主表**——主表只放 `raw_uri` + `raw_hash`，单行从 5–50KB 降到 ~1KB
2. **查询接口可路由**——语义层字段 → 后端 SQL 的编译层，不散落裸 SQL
3. **狩猎从第一天就是异步的**——`POST /hunt → 轮询`，即使现在只要 200ms

### 6.3 检索：不自研发语言

三家国内厂商（阿里 SPL、腾讯 CQL、火山检索语法）全部收敛到同一个结构：**`过滤条件 | SQL`**——过滤用索引，聚合用 SQL-92，管道符连接【官方文档；火山部分基于搜索摘要，见 04 §8】。这个形态用户已有肌肉记忆。

```
@actor.user.name = "alice" AND @severity_id >= 3 | SELECT count(*) GROUP BY src_endpoint.ip
└──────────────── 过滤表达式（编译成 WHERE）──────┘   └────── SQL 片段（AST 校验透传）─────┘
```

查询执行层要求单条 SELECT、表白名单、AST 级字段白名单和行数上限，不依赖调用参数自报范围。模型查询契约还需满足：**模型拿到的 schema 里根本没有任何字段能携带 SQL/SPL/自由文本**，CI 断言 schema 而不是断言代码——"schema 才是真正约束模型的东西"。

## 7. 共享包（库，不是服务）

判断标准：**被多个模块引用 + 不独立对外提供服务 = 库**。服务化只会增加网络开销和版本漂移。

**已交付（Go，`src/packages/go/`）**：

| 包 | 内容 | 为什么是库 |
|---|---|---|
| `result` | 统一结果码与 HTTP 状态映射 | 跨模块契约，错误码必须只有一处定义 |
| `httpx` | 请求绑定与通用中间件 | 所有 Gin 服务共用，各自实现必然漂移 |
| `logging` | 结构化日志 | 日志格式要全平台一致才能关联排查 |
| `configuration` | YAML + 环境变量加载与校验 | 配置解析规则只能有一份 |
| `cache` | Redis 客户端与类型化 key 模板 | key 前缀集中定义，避免散落拼接 |
| `iamclient` | IAM 授权接口的客户端 | 调用方不该碰 IAM 私有实现或表 |

**规划中（随对应服务落地）**：

| 包 | 内容 | 为什么是库 |
|---|---|---|
| `llmclient` | llm-gateway 的客户端 | 与 `iamclient` 同款：类型化请求、错误映射、不暴露 Bifrost 类型 |
| `contracts` | OCSF 模型、枚举、查询 IR、RequestContext | 全部服务共用，服务化只有网络开销 |
| `connectors` | 厂商模板 + 归一化 profile + 回归样本 | 只被 ingestor 引用，独立版本化 |
| `orchestrator` | workflow 引擎：10 类节点、持久化审批暂停、幂等键 | correlator/agent/soar 复用；处置动作是 tool 节点调用的工具，不是节点类型——否则每接一个厂商就要改引擎 |
| `audit` | 追加式哈希链审计 | 审计必须内嵌在每个写入点，不能是旁路服务 |

边界：**跨语言依赖通过公开契约隔离**。Python 服务调模型走 `llm-gateway` 的 HTTP 接口（经 `llmclient` 的对应实现或直接 HTTP），不内嵌 Go 库；不因语言选择生出多套协议真源。

## 8. 工程标准（每个组件强制，CI 检查）

| # | 标准 | 条款 |
|---|---|---|
| 1 | **队列消费语义** | 至少一次投递 + 消费幂等键 + 指数退避重试 + DLQ 死信——写死为事件总线协议，不是各消费者自己发挥 |
| 2 | **可观测** | 结构化日志（Go 用 `log/slog` 经 `logging` 包，Python 用 structlog）+ **OpenTelemetry 全链路 trace**：请求 → 队列 → 工具调用 → LLM 调用（每次 LLM 调用一个 span，模型/耗时/token 直接可见） |
| 3 | **健康检查与优雅停机** | 每个角色强制 `/healthz` `/readyz`；SIGTERM 优雅排水（处理完在途消息再退）；K8s preStop 对齐 |
| 4 | **授权可验证** | 每个受保护路由声明权限键并由 IAM 判定；资源归属由所属模块在查询与事务中校验；CI 断言路由声明的权限键都在权限目录内——未登记的权限键 = 构建失败（机器查人，不是人管机器） |
| 5 | **声明式种子** | 预置角色矩阵等种子数据是代码常量，启动幂等同步（不许手改库） |
| 6 | **错误码注册表** | 错误码集中定义一处，API 文档自动带出；禁止散落字符串 |
| 7 | **数据库迁移** | 每个模块自有 `migrations/` 目录，迁移文件即版本历史。Go 用 goose（`github.com/pressly/goose/v3`），服务提供 `migrate` 子命令；Compose 用一次性迁移任务在服务启动前完成 |
| 8 | **设计原则** | **正确性由机器保证，不靠人的记忆**：policy 自动建、种子自动同步、隔离自动断言——一切"手动维护/人肉纪律"的方案不进入本系统 |

> 注：只有共享结果码与权限常量是**生成**的（`scripts/generate-catalogs.mjs` 从 `result` 与 IAM 权限目录生成 Go 与 Web 的常量），其余契约以模块自有 DTO 为准，不做 proto/OpenAPI 三端生成——不为多语言生成设施付出成本，需要时再单独评估。

## 9. 当前规划的资源边界
